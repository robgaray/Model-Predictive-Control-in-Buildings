# execution_flow.md

This document walks through `30_Simulation/Main.R` and every script and function it runs, in the order in which they run. `Main.R` loads the simulator and calls `run_simulation()` (`03_Functions/run_simulation.R`), which holds the steps below. For each step it explains what the step does, what it calls, and why the step is needed.

It follows the structure of `run_simulation()` itself: four blocks, A to D, made of the numbered steps 1 to 15. Step 1 also covers the part of the run that `Main.R` does before it calls `run_simulation()`. Block B, the pre-processing, is split into four groups of steps, B.1 to B.4, as in the code.

It complements two other documents. `90_Structure/relations.csv` lists every call relation, and `90_Structure/Main_relations.md` draws them as a tree. This document adds the order in which things happen.

Convention: a file name that ends in `.R` refers to `30_Simulation/04_Scripts/*.R` unless `03_Functions/` is written. A name with brackets, such as `subset_period()`, is a function of `30_Simulation/03_Functions/`, the functions of the system. The code of the type of model Building is in `30_Simulation/05_Models/01_Building/`: its functions in `03_Functions/`, its scripts in `04_Scripts/` and its C++ files in `03_1_Functions_Cpp/`. It is written with its folder, `05_Models/01_Building/03_Functions/`, where its place matters. The other types follow the same layout: the photovoltaic installation in `30_Simulation/05_Models/02_Photovoltaic/` and the battery in `30_Simulation/05_Models/03_Battery/`, whose C++ files are in its own `03_1_Functions_Cpp/`.

## A. Initialization and parameter loading

### 1. Initialization

**What it does.** `Main.R` loads the simulator into an environment of its own, `sim`, and then calls `run_simulation()` from it. The first step of `run_simulation()` checks its arguments and sets the paths of the configuration files. Loading the simulator removes nothing from the global environment, so it can be loaded into an R session that already holds other objects, or loaded twice.

The work is done by `initialize_simulator()` (`03_Functions/initialize_simulator.R`). `Main.R` sources that file first, so the function exists, and calls it with the `30_Simulation/` folder under the working directory. The function first sets `options(stringsAsFactors = FALSE)`.

Then it builds the `paths` list. It holds the path of every data file (`30_Simulation/01_Data/*.rds`), every configuration file of the system under `30_Simulation/02_Config/`, every validation table under `02_Config/00_Validation/`, the output folder, and the C++ modules of the types of model (`paths$cpp_source_path`). The names of the configuration files and validation tables are read from `02_Config/00_Inner_parameters/04_File_paths.csv` by `read_file_paths_table()`, one row per key, with a scope: `system` for a file common to the whole simulation, or the type of model whose every asset holds the file. `paths$<key>` is the file of each `system` row, and `paths$config_path` is the configuration folder. The files of an asset are not in `paths`: each asset has a folder, `20_Assets/<asset_id>/` (the row `asset_config_folder`), and `build_asset_paths()` gives the files of its type, the rows whose scope is that type, relative to it. The GUI and the verification battery read the same file, so no code keeps a list of its own; when it is missing or lacks a key, the GUI takes the default paths of `02_Config/00_Validation/Default_04_File_paths.csv`. Only the data files, the output folder and the C++ modules, which are not configuration, are named in `initialize_simulator()`. Each file is validated against its rules of the parameter catalogue, found by the name of that file, taken from `paths`.

It checks that every folder and every file of `paths` exists, and stops with a clear message if one is missing. This way a missing file is reported at once, not later as an obscure "file not found" error. The two data files are the exception: they are checked when they are read, in step 2, so that the simulator can be loaded without any input series.

**What it calls.**

- `initialization(paths$library_file, function_paths, sim)`, from `03_Functions/initialization.R`. It does two things:
    - It sources every file of `30_Simulation/03_Functions/`, and then every file of the `03_Functions/` folder of each type of model of `30_Simulation/05_Models/` (found by listing that folder, so that a new type needs no change here), into `sim`. After this, every function of the simulation is defined in `sim`, and the functions call each other there. The parent of `sim` is the global environment.
    - It reads `00_Inner_parameters/00_Libraries.txt` line by line, skipping comments and blank lines, and loads each package, in the order of the file, with the startup messages of the packages suppressed. A missing package is installed first, and a `LOAD` line says so. This makes every dependency (`GA`, `doParallel`, `Rcpp`, and the others) available before any code uses it. The functions are sourced first so that `console_message()` exists when a package has to be installed.
    - When all goes well it writes one `LOAD` line with `console_message()`: the packages and the number of function files.
- `Rcpp::sourceCpp()` on each C++ module of the types of model, `paths$cpp_source_path`: the `.cpp` files of the `03_1_Functions_Cpp/` folder of each type, into `sim`. The building has one, `30_Simulation/05_Models/01_Building/03_1_Functions_Cpp/period_simulation_cpp.cpp`. It compiles the C++ thermal engine and makes `period_simulation_cpp()` callable from R. The same call compiles the headers the file includes, which hold the electrical model of the heat pump: `heat_pump_cop_cpp()`, `heat_pump_electricity_cpp()` and `apply_commitment_margin_cpp()` become callable from R too. The simulation and the R functions that need the electricity of an itinerary (`heat_pump_cop()`, `heat_pump_electricity()` and `apply_commitment_margin()`, and through them `building_margin_data()` and `building_margin_energy()`) therefore use one compiled electrical model. The battery has one too, `30_Simulation/05_Models/03_Battery/03_1_Functions_Cpp/battery_trajectory_cpp.cpp`. It compiles the physics of the stored energy of a battery and makes `battery_trajectory_cpp()`, `battery_free_trajectory_cpp()`, `battery_recovery_correction_cpp()` and `battery_factor_search_cpp()` callable from R, which `battery_trajectory()`, `battery_free_trajectory()`, `battery_recovery_correction()` and `battery_factor_search()` call once they have checked their inputs. The two bisections of the windows of a battery, that of its factor and that of the correction of its Recovery Phase, therefore run every value they test in compiled code. Every module is compiled once, here, because compiling it at every call would be far too slow. Each module adds a few seconds to the start of every process that loads the simulator, also when no asset of its type is in the registry.

After the compilation it writes one `LOAD` line with the number of C++ modules compiled. `initialize_simulator()` keeps `paths` in `sim` and returns `sim`. `Main.R` then takes `run_simulation` from `sim`. The function keeps `sim` as its enclosing environment, so it finds there every function of the simulator, and nothing is attached to the search path.

Then `run_simulation(config_path, overrides, data_path, output_path)` starts. `Main.R` gives it the folders `02_Config`, `01_Data` and `90_Output` of `30_Simulation/`, and no overrides (`NULL`). It stops if `config_path` or `data_path` is not a folder. When there are overrides (a table with the columns `file`, `parameter` and `value`, where `file` is written as `@<key>`, a key of `04_File_paths.csv`, as `@<asset_id>/<key>` for a file of an asset, or as a file name), `apply_config_overrides()` (`03_Functions/`) resolves the keys with `resolve_config_key()` through the file paths table of the folder and writes a temporary copy of `config_path` with them applied, and the run reads that copy instead. The overrides are applied to the files, before anything is loaded, so every overridden value is validated against the parameter catalogue as a value of the file would be. The copy is removed when the run ends. It takes `paths` from `sim`, and `build_config_paths()` (`03_Functions/`) reads `04_File_paths.csv` of `config_path` and gives the path of every system configuration file in that folder, which replace those of `sim$paths`. It stops, naming them, if any of these files is missing. The input series are read from `data_path` and the output tables are written to `output_path`. This way a run reads its configuration and its data from the folders it is given, and not from the folder the simulator was loaded with. `initialize_simulator()` uses the same function to build the paths it keeps in `sim`.

**Why.** Nothing else can run without this step: neither the functions of the system and of the types of model nor the C++ engine would exist. Keeping them in `sim` rather than in the global environment lets the simulator be loaded next to other work in the same R session.

### 2. Load data and model parameters

**What it does.** `run_simulation()` calls `load_all_parameters()` (`03_Functions/`), the single entry point that loads the data and every parameter. It returns `Main_df`, `assets` and `parameters`. The loaders it sources run inside the function, so nothing is left in the global environment.

The data are held in two kinds of table. `Main_df` holds what is common to every asset (the time grid, the weather, the prices and, later, the market calendar) and the balances of the system: its net electricity in each itinerary, the flexibility it commits and its cash flows. The table of each asset, `assets[[asset_id]]$df`, holds the columns of that asset (for a building, its temperatures, setpoints, comfort, heat and electricity), one row per row of `Main_df`, with the column `time` as the key of its rows. The net electricity is the one column both hold: `Main_df` holds the sum over the assets of the column of the same name of each asset.

When all goes well, the loading writes few lines to the console, all through `console_message()`: one `LOAD` line for the internal parameters (`load_internal_parameters.R`), one `DATA` line for `Main_df` (`assemble_main_df.R`, which also writes a `WARNING` line when it trims the end of a series), one `LOAD` line per asset (`load_12_asset_registry.R`), one `LOAD` line for the configuration files (`load_configuration_files.R`) and one `DATA` line per asset with the size of its table (`load_all_parameters()`). The loaders, the validations and the type loaders write nothing, and a validation warning is raised with `call. = FALSE` so that it does not name the internal call.

It runs in four blocks, in this order:

- **A. Internal parameters.** What the rest of the script and the loaders need before any configuration file of `02_Config` is read:
    1. **The validation tables.** `load_parameter_catalogue()` reads `00_Validation/Parameter_catalogue.csv`, which gives, for every configuration file and every parameter, its type (`Integer`, `Real`, `Options` or `Text`), its severity (`Error` or `Warning`), its valid range or options and its default value. It checks that every rule can be applied, and reads the integer tolerance of `00_Validation/Validation_tolerances.csv`. Every loader validates its file against these rules; a missing parameter stops the run, and the message gives its default value. It also reads the plausibility bounds of the simulation (`00_Validation/Validation_bounding_simulation.csv`).
    2. **The internal parameters.** `load_internal_parameters.R` loads them, in this order:
        - **The computing parameters.** `load_parameter_file()` fills `parameters$computing` from `00_Inner_parameters/01_computing_parameters.csv`. These are the numerical constants of the engine: the resolution of the master time grid (`main_resolution_sec`, 300 s), the tolerance below which planned energy counts as zero, the margin kept between generated flexibility events, and the lead times of the price bands. They are loaded before `Main_df` because its assembly needs the grid resolution.
        - **`load_03_physical_properties.R`** fills `parameters$physical_properties` from `00_Inner_parameters/03_Physical_properties.csv` (`Cp_air`, `dens_air`). `validate_physical_properties()` checks that both are positive and warns when they differ from the reference values.
        - **`load_16_debug_and_config.R`** fills `parameters$debug_and_config` from `16_Debug_and_config.csv`: `month_subset`, `period_subset`, `verbose`, `parallel`, `parallel_workers`, `Price_emulation` and `random_seed`. `verbose` becomes a logical switch.
        - **The needed columns.** `load_needed_columns()` (`03_Functions/`) reads `00_Inner_parameters/02_Needed_cols.csv`, the one list of the columns of the simulation data, and checks it against the parameter catalogue. Its column `table` says whether each column belongs to `Main_df` (`system`) or to the table of the assets of a type of model (the name of the type, for example `Building`): each type has its own list of columns. Its row `@System_variables_df` stands for the columns of the registry of the system, `01_Model_Descriptions/00_System/Simulation_Variables_System.txt`, and its row `@<type>_variables_df` (for example `@Building_variables_df`) for those of the registry of the type, for a building `01_Model_Descriptions/01_Building/Simulation_Variables_Building.txt`. The registry of each type is the one its contract names (`model_type_contract()`, operation `variable_registry`). `itinerary_columns()` names the columns of the four itineraries from the variables of the registries of the types of the assets of the registry only. `variable_registry_columns()` (`03_Functions/`) reads them, so each column is declared in its registry only. A column may be in `Main_df` and in the table of a type only when it is the net electricity of the system in an itinerary (`system_net_energy_columns()`) or an input of that type; any other stops the run. A row of stage `input` declares an input: a column of `Main_df` that the table of every asset of the type holds a copy of during the whole run. Its table must be a type (not `system`), its column must be a column of `Main_df`, and it cannot be a net electricity column. The inputs are in `parameters$asset_cols`, and `parameters$asset_input_cols` holds them by type. `parameters$needed_cols` holds every column `Main_df` must have before the simulation loop starts, and `parameters$asset_cols` a list with one element per type of model, each with every column of the table of an asset of the type, `time` first; `simulate()` creates any that is missing. `parameters$needed_cols_assembly` and `parameters$asset_cols_assembly` hold the columns of stage `assembly`, those each assembled table must already hold (the second one, by type). `parameters$joined_cols` holds every column of `Main_df` and of the tables of every type, once, in the order of the file, which is the order of the pieces the markets work on. The output tables follow the same order: `Main_df_computed` the columns of `Main_df`, and the table of each asset `time` and then the columns of its type. `parameters$itinerary_variables` holds, for each type, the variables that its registry expands into the four itineraries; `itinerary_columns()` (`03_Functions/`) builds from them the columns of one itinerary, those of every type once each, so the code never finds an itinerary by the suffix of its columns.
- **B. `Main_df`.**
    3. `assemble_main_df.R` builds it, as described below.
    4. `validate_Main_df()` (`03_Functions/`) checks it, as described below.
- **C. Parameters.**
    5. **The configuration files.** `load_configuration_files.R` loads every configuration file of `02_Config`, in the order of their numbers, and then the asset registry, as described below.
    6. **Relations between parameters.** `validate_parameter_relations()` (`03_Functions/`) checks the rows of `00_Validation/Validation_parameter_relations.csv`: relations two parameters have to keep, which the range of each one cannot express, such as the low end of a comfort band below its high end, the heating and cooling setpoints of each mode at least `Deadband` apart, or the implementation horizon not longer than the optimization horizon. It checks them once per asset, looking for each name first in the groups of the asset and then in the other groups of `parameters`. A relation applies to the assets of its `asset_type` column (or to every asset, with `-`), and is checked against the scopes of `04_File_paths.csv`: a file or type it names that the table does not hold stops the run, and so does a parameter that is not found in a relation that applies. The run stops listing every relation that fails. The GUI applies the same rows before saving.
    7. **`T_ext_24h`.** `Main_df$T_ext_24h` is recalculated as the mean of `Text` over the previous calendar day. On the first day, which has no previous day, it takes `parameters$forecast$t_ext_24h_default`, and the run stops if that value is missing.
- **D. The tables of the assets.**
    8. For each asset of the registry, `load_all_parameters()` takes the contract of its type of model (`model_type_contract()`) and calls its operation `new_table`, which builds the table of the asset on the time grid of `Main_df`. For a building, `building_new_table()` (`05_Models/01_Building/03_Functions/`) calls `generate_variables_df()` (`03_Functions/`), which builds the table from the variable registry of the building, with every column at its initial value, and then sets `Occupancy` and `Scheduling` to 0 as integer columns; both are generated later, in step 6 of `run_simulation()`. `validate_asset_df()` (`03_Functions/`) checks that the table has the rows of `Main_df`, with the same `time`, every required column (those of `parameters$asset_cols_assembly` for its type), numeric, `Occupancy` and `Scheduling` integer flags, only 0 and 1 in the flags, and only 0, 1 and 2 in `Act_heat_exec` and `Act_cool_exec`; a flag is checked only when the type of the asset holds it. `assets[[asset_id]]$df` is the table. Then `copy_asset_inputs()` (`03_Functions/`) gives the table of each asset a real copy, not the same vector, of the columns of `Main_df` that the type of the asset declares as inputs (`parameters$asset_input_cols`). `T_ext_24h` is already final, and `subset_period()` cuts both tables by the same rows afterwards.

**How `Main_df` is assembled.** `assemble_main_df.R` runs these steps:

1. It loads and checks the two real input tables. `load_meteo_df.R` reads `Meteo_df` (`Text`, `SolarR`). `load_energy_prices_df.R` reads `Energy_Prices_df` (`Elec_unit_cost_buy`, `Elec_unit_cost_distribution`, the four `Flex_unit_cost_*` columns, `Flex_Probab_down` and `Flex_Probab_up`). Each script first stops with a clear message if its file is missing. Each table is checked for an evenly spaced time step, for a step and an origin that fit the master grid, for its data types, and for its value ranges (`Validation_Meteo_df.csv` and `Validation_Energy_Prices_df.csv`).
2. It sets the common time range. Both tables must start at exactly the same instant, or the run stops. If they end at different instants, the longer one is cut to the end of the shorter one, and a `WARNING` line says how many rows were dropped and from which table.
3. It builds the master time grid over that range, with one row every `main_resolution_sec` seconds.
4. It places both tables on the grid. The weather is interpolated linearly. The prices are held constant over each of their own steps, because a price applies to the whole interval it was quoted for. A row holds the energy of the time step that ends at its instant, so it takes the price in force at the start of that step. The first row has no step before it and takes the first price.
5. It generates three synthetic tables directly on the grid, all at 0:
    - `System_variables_df`, through `generate_variables_df()`. It takes its columns from `variable_registry_columns()`, which reads `02_Config/01_Model_Descriptions/00_System/Simulation_Variables_System.txt`: the net electricity of the system, the flexibility it commits on each leg and its cash flows. A variable marked `scenario = yes` becomes four columns, one per context (`_exec`, `_plan`, `_plan_flex_down`, `_plan_flex_up`); a variable marked `scenario = no` stays as one column.
    - `Flexibility_actions_df`, with `Flex_Act`.
    - `Meteo_transformations_df`, with `T_ext_24h`, `Text_forec`, `SolarR_forec` and `T_ext_24h_forec`.
6. It joins everything into `Main_df`.
**How `Main_df` is validated.** `validate_Main_df()` (`03_Functions/`) checks that `Main_df` is a non-empty data frame with every required column (those of `parameters$needed_cols_assembly`); that `time` is a strictly increasing `POSIXct` with no `NA`; and that every other required column is numeric. It also checks plausibility against `Validation_bounding_simulation.csv`: `Elec_unit_cost_buy` below its bound only raises a warning, while a negative `SolarR` stops the run. `Text` is not checked again: it is the weather input, interpolated, and its range was checked when the weather was read.

**How the configuration files are loaded, in execution order.** A file of parameter and value lines is loaded by `load_parameter_file()` (`03_Functions/`). It reads the file through `read_and_validate_parameter_csv()`, which rejects duplicated names and checks each value against the parameter catalogue through `validate_parameter_config()`. The run stops when the file has no rule, when it holds a parameter no rule describes (the message names the closest rule, since that is usually a misspelt name), when a rule has an unknown type, or when a parameter is missing (the message gives its default value). Then each value takes the type of its rule: a number for `Integer` and `Real`, and for an `Options` rule whose options are all numbers; text otherwise. No parameter name is written in the code: the names come from the file and the types from the catalogue. A file that needs more than that, such as a table, has a loading script of its own. A file may also hold a block of parameters above its table. It starts with the header `parameter,value,unit`, the block runs to the first blank line, and the table is what follows that line (`split_config_sections()`, `03_Functions/`, gives the lines of each part). `load_parameter_block()` loads the block as `load_parameter_file()` loads a flat file: the rows of the catalogue that have a default value are the parameters of the block, and the rows with `-` are the columns of the table, which the script of the table validates. The run stops when the blank line that closes the block is missing, and when a row of the block names a column of the table. A file that does not start with that header is read whole, as before.

1. **The optimization parameters**, from `01_Optimization_parameters.csv`, fill `parameters$optimization`: the settings of the genetic algorithm (`population_size`, `iteration_number`, `run_number`, `pcrossover`, `pmutation`).
2. **`load_03_market_config.R`** fills `parameters$market` from `03_Market_config.csv`. The ranges and options of every value are those of the catalogue, already applied when the file is read. The relations between horizons are checked with the other relations between parameters, in step 6 above. The script checks that both optimization horizons are a whole number of market intervals. It also translates the aims of the basic market mode (`O`, `E`, `O+F`, `E+F`) into the labels the code uses (`operation`, `energy`, `operationflex`, `flexibility`) through `map_optimization_aim()`. The same file holds the six limits of the basic flexibility price emulation (`Max_flex_*`). It needs `parameters$control` and `parameters$optimization`, both loaded before it.
3. **`load_04_market_config_scheduling.R`** fills `parameters$market_config_scheduling` from `04_Market_config_scheduling.csv`, through `load_market_config_table()`. It drops the units row, checks the required columns (`Market`, `closure`, `begin`, `end`, `end_optimization`, `aim`), checks that the four time columns are numbers not below 0, checks each aim with `map_optimization_aim()`, and rejects two markets that would clear in the same market slot. The table is used only when `Complex_Market_Config` is `yes`.
4. **`load_05_market_config_piloting.R`** does the same for `05_Market_config_piloting.csv`, into `parameters$market_config_piloting`.
5. **The energy price parameters**, from `06_Energy_price_parameters.csv`, fill `parameters$energy_price`: the export and sell discounts (`Energy_Export_discount`, `Energy_Sell_discount`) and the four `Price_variation_*` premiums, one per band of lead time. Steps 9 and 10 of `run_simulation()` use them.
6. **The flexibility price emulation parameters**, from `07_Flexibility_price_emulation_parameters.csv`, fill `parameters$flexibility_price_emulation` (`Max_shift_hours`, `P_advance`, `P_delay`, `P_event_base`, `decay_rate`). They are used only by the market-aware mode of step 8 of `run_simulation()`.
7. **The flexibility event parameters**, the fifteen of `08_Flexibility_Event_Configuration.csv`, fill `parameters$control`. They define the flexibility events: the length of their phases, when the Recovery Phase counts as converged, which system provides an upward event, when a window is feasible, and the tolerances and margin of a commitment.
8. **The reward parameters**, from `09_Reward_parameters.csv`, fill `parameters$reward`: the weight of cost (`alpha_cost`) and `Revenue_discount_per_hour`. The economy is of the system. The comfort weight and the comfort bands are not in this file: each building has its own, in `18_Comfort_parameters.csv` of its folder (item 10).
9. **The forecast parameters**, from `15_Forecast_parameters.csv`, fill `parameters$forecast`: whether the weather forecast and the price forecast are `accurate` or `inaccurate`, how many days of history the weather forecast uses and how fast that history gains weight, and `t_ext_24h_default`.
10. **`load_12_asset_registry.R`** fills `parameters$assets` from `12_Asset_registry.csv`, the list of the assets of the system, one row per asset with its `asset_id` and its `asset_type`. It is loaded last, although its number is 12, because each asset takes the physical properties loaded before it. It drops the units row with `drop_unit_row()`, checks each asset against the catalogue with `validate_parameter_config()`, and checks that the ids are unique and are the type followed by an underscore and three digits. The registry may hold several assets, and the shipped one holds one building. It also checks that every type of model that holds files in `04_File_paths.csv` is an asset type of the catalogue. Each asset has its own configuration folder, `02_Config/20_Assets/<asset_id>/`, with the files of its type of model. For each asset, `build_asset_paths()` (`03_Functions/`) gives the paths of those files (the rows of the file paths table whose scope is its type), and stops, naming the asset, if its folder or one of its files is missing. Then `model_type_contract()` gives the operations of its type, and the operation `load_parameters` reads the files of the asset and returns its groups. For a building it is `load_building_parameters()` (`05_Models/01_Building/03_Functions/`), which sources the loading scripts of the building, in `05_Models/01_Building/04_Scripts/`, and loads, in this order, with the paths of the asset:
    - **The operational temperature corrections**, the eight of `10_Operational_temperature_corrections.csv`. They shape the reference temperatures: how long before and after occupancy the building is prepared, how much the comfort band is shifted then, and how the heating and cooling seasons are detected.
    - **`load_11_model_parameters.R`**, `parameters$model` from `11_Model_parameters.csv`: the capacitances and resistances of the thermal model, the surfaces, the heat pump curves, the ventilation rates and the initial state. `validate_model_parameters()` checks that the building volume is positive and plausible, which the range of the catalogue cannot express, and `compute_Rvent()` turns the air renewal rates (`RENvent01`, `RENvent1`, `RENvent2`, in air changes per hour) into ventilation resistances (`Rvent01`, `Rvent1`, `Rvent2`, in K/kW), plus their heat-recovery versions. It needs `parameters$physical_properties`, loaded in block A.
    - **`load_13_modes_setpoints.R`**, `parameters$setpoint_modes` from `13_Modes_setpoints.csv`. It reads the table directly, because it is a table and not a list of parameters: the whole file, or the part below the block of parameters when the file holds one. The block, which holds `Deadband`, is read apart by `load_parameter_block()` (see below). It checks the `mode`, `heating` and `cooling` columns, the absence of `NA`, and that the modes are consecutive whole numbers starting at 1. That is what lets `optimize_modes()` treat a mode as a whole number between 1 and the number of modes.
    - **`load_14_use_patterns.R`**, `parameters$use_patterns` from `14_Use_Patterns.csv`. That file holds two tables: a `TYPE` block with 24 hourly columns (`H01` to `H24`) and a `MONTH` block with 7 weekday columns (`D01` to `D07`). The script finds and separates both, checks their columns and types, and checks that every type the `MONTH` block uses exists. Step 6 of `Main.R` uses the result.
    - **The comfort group**, `parameters$comfort` of the building, from `18_Comfort_parameters.csv`, read by `load_parameter_file()`: the comfort weight `alpha_comfort` and the service and setback comfort bands. Each building has its own values.
    - **The control group**, the block of parameters of `13_Modes_setpoints.csv`, read by `load_parameter_block()`: `Deadband`, the width of the hysteresis band around each setpoint. The block starts the file, under the header `parameter,value,unit`, and ends at the first blank line, after which the table of the modes begins. The block is validated against the catalogue rows of the file that have a default value, as a flat file is. The group is named as the catalogue names it, `control`.

    `parameters$assets$Building_001` then holds `asset_id`, `asset_type` and the six groups of the building: `model`, `operational_temperature_corrections`, `setpoint_modes`, `use_patterns`, `comfort` and `control`, which holds `Deadband`. The parameters of the building are read in one place only, its entry of `parameters$assets`. Every operation of the type of model of the building receives that entry as `asset` (see `model_type_contract()` in step 13), and so do the functions of the building that those operations call. The `asset_type` of the asset names the type of model whose operations the market, the genetic algorithm, the reward and the execution call (see `model_type_contract()` in step 13). The parameters held by `08_Flexibility_Event_Configuration.csv` make `parameters$control`; `parameters$control` and the `control` group of the building are two different lists.

    For a photovoltaic installation (`Photovoltaic_001`), the operation `load_parameters` is `load_photovoltaic_parameters()` (`05_Models/02_Photovoltaic/03_Functions/`). It reads the one file of the installation, `17_Photovoltaic_parameters.csv`, with `load_parameter_file()`, and returns three groups: `photovoltaic`, with its 15 parameters (location, solar radiation, orientation, modules and inverter), `reference_conditions`, a copy of the four reference conditions of the modules of `parameters$physical_properties` (`PV_STC_irradiance`, `PV_STC_cell_temperature`, `PV_NOCT_irradiance` and `PV_NOCT_ambient_temperature`), and `sun`, a copy of `Solar_constant`. `validate_physical_properties()` warns if one of the five differs from its reference value in `Validation_03_Physical_properties.csv`. The relations of the comfort bands and of the setpoints of the modes belong to the buildings (`asset_type` `Building`), so they are not checked for an installation.

    For a battery (`Battery_001`), the operation `load_parameters` is `load_battery_parameters()` (`05_Models/03_Battery/03_Functions/`). It reads the one file of the battery, `19_Battery_parameters.csv`, with `load_parameter_file()`, and returns one group, `battery`, with its 9 parameters (capacity, limits of the state of charge, power limits, efficiencies and self-discharge). The relations of the state of charge (`SOC_min` below `SOC_max`, and `SOC_initial` between them) belong to the batteries (`asset_type` `Battery`) and are checked in step 6 of `load_all_parameters()`, once every parameter is loaded.

**Why.** After this step, `parameters` holds everything the rest of the simulation needs, already validated, and `Main_df` and the table of each asset hold the whole year, not yet cut to the simulated period. Every file is validated against the one catalogue as it is read, so each file fails on its own, and adding a parameter is one line of its file and one row of the catalogue.

## B. Pre-processing

When `verbose` is TRUE, the pre-processing writes `PREPARE` lines with `console_message()` and nothing else: the period and the random seed (after step 5), one line per asset (after its `prepare_period`, step 6), the price signals (after step 9) and the size of the economic analysis (written by `prepare_economic_analysis()`, step 12). `subset_period()`, `prepare_flexibility_prices()`, `prepare_energy_prices()` and the preparation of the building write nothing.

### B.1 Random seed

#### 3. Fix the random seed

**What it does.** Inline code in `run_simulation()` calls `set.seed(parameters$debug_and_config$random_seed)`, so that two runs of the same configuration give the same result. It sits here because this is the first point where the parameter exists and no random number has been drawn yet.

Five parts of the simulation draw random numbers: `prepare_flexibility_prices.R`, `generate_flexibility_events.R`, `place_flex_candidate.R`, `try_flex_echo.R` and the operators of the genetic algorithm. Without a fixed seed no two runs can be compared.

`random_seed = 0` means "do not fix the seed": the run then uses the random state of the system and is not reproducible.

**Parallel workers.** `set.seed()` only affects the main process. When `parallel == 1`, the genetic algorithm runs on a cluster of worker processes, each with its own random stream. So `start_worker_cluster()` calls `parallel::clusterSetRNGStream()` with the same seed right after creating the cluster, once, before the simulation loop (see step 13). The number of workers is `parallel_workers` in `30_Simulation/02_Config/16_Debug_and_config.csv`. When it is 0, the default, the simulation uses all logical cores but one, as returned by `parallel::detectCores()`.

The result does not depend on the number of workers, and it is the same in series and in parallel: the same seed gives the same result in every case. The genetic algorithm evaluates its population through the `%dorng%` loop of the `doRNG` package, which draws one random number of the main process per generation. A plain loop would draw none, and the two modes would then follow different random sequences. So the genetic algorithm always runs that loop: in parallel on the worker cluster, and in series in the main process, one candidate after another. That is why `doRNG` is one of the required libraries of `00_Inner_parameters/00_Libraries.txt`.

### B.2 Climate and period

#### 4. Climate priority

**What it does.** For each asset, `run_simulation()` takes the contract of its type of model and calls its operation `prepare_year`, which prepares the table of the asset with what needs the whole year of data. For a building, the operation is `prepare_climate()` (`05_Models/01_Building/03_Functions/`), which writes `Overall_Climate` into the table of the building, a daily tag: `"Heating"`, `"Cooling"` or `"Intermediate"`. It reads the outdoor temperature `Text` from `Main_df`, which is common to every asset, and the thresholds from the `operational_temperature_corrections` of the building. For each calendar day it looks at each of the previous `HDD_period` days on its own. If every one of them has a mean `Text` below `T_ref_Heating_Season`, the day is `"Heating"`. Otherwise it looks at the previous `CDD_period` days the same way: if every one has a mean `Text` above `T_ref_Cooling_Season`, the day is `"Cooling"`. Otherwise it is `"Intermediate"`. Each day of the window is checked on its own; the window is not averaged as a whole. A day whose previous days reach back before the first day of the series has no full history: it is checked on the first `HDD_period` (or `CDD_period`) days of the series instead. With `HDD_period = 7`, every day of the first week is tagged from the first 7 days of the series. For a photovoltaic installation, the operation is `photovoltaic_solar_geometry()` (`05_Models/02_Photovoltaic/03_Functions/`), which writes `Sun_elevation`, `Sun_azimuth` and `Cos_incidence` into its table for the whole year. `solar_position()` computes them at the instant of each row plus `Irradiance_time_offset`, from the latitude, the longitude, the tilt and the azimuth of the installation, with the algorithm of the NOAA Solar Calculator (Meeus). It is done once, before the period is cut, so the steps only read the columns.

**Why here.** It runs before the period is cut (step 5), so that the first days of a short run still have their own previous days available. Otherwise they would be tagged from the first days of the run. Step 6 uses the tag.

#### 5. Subset `Main_df` and the table of each asset by month and period

**What it does.** `run_simulation()` calls `subset_period()` with `month_subset` and `period_subset` from `parameters$debug_and_config`, once for `Main_df` and once for the table of each asset. The rows it keeps depend only on `time`, which the tables share, so they keep the same rows. If `month_subset` is not 0, a table keeps only the rows of that month. If `period_subset` is not 0, it keeps only that many rows, counted from the start, or all of them if there are fewer.

**Why.** It allows short runs, for testing or diagnosis, without editing the data files. The shipped configuration sets `month_subset = 1` and `period_subset = 1000`: the first 1,000 rows of January, about three and a half days at 5-minute resolution.

### B.3 Profiles

#### 6. Profiles of each asset

**What it does.** For each asset, `run_simulation()` takes the contract of its type of model and calls its operation `prepare_period`, which prepares the table of the asset for the simulated period, already cut in step 5. For a building, the operation is `building_prepare_period()` (`05_Models/01_Building/03_Functions/`), which runs three functions on its table, in this order, with the groups of the building (`parameters$assets`):

1. **Occupancy.** `prepare_occupancy()` writes `Occupancy` into the table of the building, 0 or 1, from the `use_patterns` of the building. A row holds the energy of the time step that ends at its instant, so the occupancy of a row is read at the start of its step, one step before its instant, as the prices and the flexibility events are. For the start of the step of each row it finds the month and the weekday (Monday is 1), reads from the `MONTH` block which day type applies, and then reads from the `TYPE` block the value of its hour. The column `Hnn` is the hour that ends at nn:00: `H01` is the hour from 00:00 to 01:00 and `H24` the hour from 23:00 to 24:00 of the same day. The time step is read from the time column of the table, which shall be regular. It checks that the result is always 0 or 1, with no `NA`.
2. **Scheduling.** `prepare_scheduling()` writes `Scheduling` into the table of the building, 0 or 1, from its `Occupancy` and two parameters of the `operational_temperature_corrections` of the building, `Service_Anticipation_Begin` and `Service_Anticipation_End`, in hours. The day of a row is the date of the start of its time step, as for the occupancy. For each day with at least one occupied row, it takes the first and the last occupied instants, moves the first one earlier by `Service_Anticipation_Begin` and the last one earlier by `Service_Anticipation_End`, and sets `Scheduling = 1` over that window.
3. **Reference temperature profiles.** `prepare_comfort_bands()` writes four comfort band columns into the table of the building. The bands come from the `comfort` group of the building, and their shifts from the `operational_temperature_corrections` of the building:
    - `Service_T_Low` and `Service_T_High`: the service band (`Service_T_Low/High`) where `Occupancy` is 1, and the setback band (`Setback_T_Low/High`) where it is 0. The setback band is not a comfort target. It is defined to keep the building out of regions of undesired behavior, for the integrity of the system.
    - `Scheduling_T_Low` and `Scheduling_T_High`: the same as the service columns, except where `Scheduling` is 1. There the service band applies, even before people arrive, and it is shifted by the climate of the day. On a `"Heating"` or `"Intermediate"` day, `Service_AT_Low_Sched_HDD` is added to the lower limit. On a `"Cooling"` or `"Intermediate"` day, `Service_AT_High_Sched_CDD` is subtracted from the upper limit. The result is then intersected with the service columns, so `Scheduling_T_*` is always the more restrictive of the two bands. If the intersection is empty on any row, the run stops.

**Why.** `Occupancy` is the start of the group: the scheduling window uses it to decide when to prepare the building, and the comfort bands use it to choose between the service band and the setback band. `Scheduling` marks when the building has to be prepared, heated or cooled in advance, before people arrive, and the comfort bands use it for the planning band. `period_calculation()` measures comfort against the `Service_T_*` band for the executed trajectory, and against the `Scheduling_T_*` band while planning. The flexibility itineraries are measured against `Service_T_*` on the rows of their window (Commitment, Neutral and Recovery Phases) and against `Scheduling_T_*` elsewhere. This way the optimizer plans the preparation with its own band without relaxing the comfort really required when the building is used. Each asset prepares its own table, so the order between assets does not matter: they share no column of these profiles.

### B.4 Markets and prices

#### 7. Market columns and market events

**What it does.** `run_simulation()` calls `prepare_market_calendar()`, which first assigns every row of `Main_df` to its market interval, in `Main_df$MarketUTC`. This is the only place where `MarketUTC` is computed. A row holds the state of the building at its instant and the energy of the time step that ends there. So a row belongs to the interval that contains its time step, which is the interval of the instant one step earlier. With this rule, the energy of an interval is exactly the energy of the time steps inside it. For example, with 5-minute steps and 15-minute intervals, the interval from 00:00 to 00:15 holds the rows of 00:05, 00:10 and 00:15. The first row is the initial condition: its step lies before the simulation, so it belongs to the interval before it and holds no energy.

Then it sets to 0 the twelve market columns of `Main_df`: for Scheduling (`Sched_`) and for Piloting (`Pilot_`), the market name, the bid time, the start and end of the period, the end of the optimization horizon and the aim. Then it calls `build_market_timeline()` (`03_Functions/`) once per role. It writes every market on the row of its bid time, in one of two modes:

- **Basic** (`Complex_Market_Config = "no"`): a single market repeated every `Implementation_horizon_*` hours over the whole period, always with the same aim.
- **Complex** (`Complex_Market_Config = "yes"`, the shipped configuration): each row of the market configuration table is one type of market (day-ahead, intraday, and so on). For each day of the period, one instance of each is created: `begin` is counted from midnight, `end` is the length of the period after `begin`, and `closure` is counted back from `begin`. An instance whose bid time does not fall on a row of `Main_df$time` is dropped with a warning.

In both modes every time is cut to the range of the simulation. A market whose period is left with no length, because it falls at the edge of the simulation or outside it, has no time step to control, so it is not placed.

Last, `validate_market_coverage()` (`03_Functions/`) checks that the time step of every row after the first falls in the period of at least one Scheduling or Piloting market: a market covers the rows after its `Period_Begin`, up to the row at its `Period_End`. If any row is left out, nothing would decide its operation, so the run stops with an input data validation error that names the uncovered stretches.

Then `build_market_events()` (`03_Functions/`) reads, once, the table of the market events of the run out of these columns: one row per clearing of a Scheduling or Piloting market, with its family, name, clearing row, market interval (`instant_market_slot()`), bid time, period, horizon and aim. A row of `Main_df` holds an event of a family when the market name of that family is set on it (`is_market_active()`). Steps 10, 11 and 12 take their rows from this table.

**Why.** At each row, the simulation loop reads these columns (`is_market_active()`) to decide whether a Scheduling market, a Piloting market, or both clear there. Every later step reads the market interval of each row from `MarketUTC`. The table of the market events locates every event in one place, so the price matrices, the commitment matrices and the economic analysis all have the same events.

#### 8. Flexibility price emulation

**What it does.** It runs only when `Price_emulation = 1`, as in the shipped configuration. `run_simulation()` then calls `prepare_flexibility_prices()`, which overwrites the flexibility columns of `Main_df` with generated values: the four `Flex_unit_cost_*` prices, `Flex_Probab_down`, `Flex_Probab_up` and `Flex_Act`. It has two modes, chosen by `Complex_Market_Config`:

- **Basic** (`"no"`): for each day it draws a number of events and one commitment price and one execution price for that day, within the `Max_flex_*` limits of `03_Market_config.csv`. `place_flex_candidate()` places each event, in whole market slots, within the day.
- **Market-aware** (`"yes"`): it calls `generate_flexibility_events()` (`03_Functions/`). First it goes through the Scheduling markets in order of bid time. For each one it offers the earlier events that have not moved yet the chance to move earlier or later (`try_flex_echo()`), when their exclusion zone overlaps the new market's horizon. The zone is `flexibility_event_margin_sec` long, 3 hours by default. Then it places new events only in the segments left free (`compute_available_segments()` and `place_flex_candidate()`). After all the Scheduling markets, it goes through the Piloting markets. It places their events without checking overlaps, and accepts each with a probability that falls exponentially with the lead time (`P_event_base * exp(-decay_rate * h)`). Its parameters are in `07_Flexibility_price_emulation_parameters.csv`.

In both modes, an event covers the rows of the market intervals it spans (`MarketUTC`), which are the rows whose time step falls inside it.

**Why.** It creates reproducible flexibility scenarios when there is no real flexibility market data. In the market-aware mode, the events follow the structure and the overlaps of the configured markets.

#### 9. Buy and sell price signals

**What it does.** This step always runs. `run_simulation()` calls `prepare_energy_prices()`, which derives twelve price columns, four for energy and eight for flexibility, from the columns already in `Main_df`:

- The four energy prices use `Elec_unit_cost_buy` as the reference price, `P_ref`, and the discounts of `parameters$energy_price`:
    - `import_buy = P_ref * factor_tiempo`
    - `import_sell = import_buy * (1 - Sell_discount/100)`
    - `export_buy = P_ref * factor_tiempo * (1 - Export_discount/100)`
    - `export_sell = export_buy * (1 - Sell_discount/100)`
- `factor_tiempo` is the premium for the lead time at which a price is quoted. These columns are the prices "now", used when a timestep is executed, so they always take the band of the shortest lead time.
- The eight flexibility columns are, for now, the buy and sell copies of the four `Flex_unit_cost_*` columns, whether they came from the data file or from step 8.

**Why.** Every later calculation reads these twelve columns, not the input prices. The prices a market sees at longer lead times are computed separately, in step 10.

#### 10. Future-horizon price matrices

**What it does.** `run_simulation()` calls `prepare_market_information()`, which builds `full_market_information`, a list of thirteen tables, one per price signal:

- the four energy prices (`Elec_unit_cost_import_buy_df`, `_import_sell_df`, `_export_buy_df`, `_export_sell_df`);
- the distribution rate (`Elec_unit_cost_distribution_df`), used only for the base energy term of the reward;
- the eight flexibility prices (`Flex_unit_cost_{down,up}_{com,exec}_{buy,sell}_df`).

Each table has one row per market event, that is, each market interval where a Scheduling or a Piloting market clears. An event is keyed by the interval its clearing instant falls in (`instant_market_slot()`): a market that clears at 12:00 is keyed by the interval that starts at 12:00, the first one whose energy is still ahead of it. It has one column per step ahead, from `"0"` to `max_steps_ahead - 1`. Column `j` holds the price of the market interval `j` steps after the event, so `j` steps is also how far ahead of the clearing that price is quoted. In order:

1. It computes `max_steps_ahead` with `compute_max_steps_ahead()`: the longest distance from a market's bid time to the end of its optimization horizon, in market steps, rounded up. It reads the market configuration in use: in basic mode, `Anticipation + Optimization_horizon` of the Scheduling and Piloting markets of `03_Market_config.csv`; in complex mode, `closure + end + end_optimization` of every market of `04_Market_config_scheduling.csv` and `05_Market_config_piloting.csv`.
2. It reads `Main_df$MarketUTC`, written in step 7, and stops if it is missing. Its rows are the market intervals of the events of the table of step 7.
3. It averages each price signal over each market interval.
4. It creates the tables with every cell missing (`NA`) and then fills every cell. Nine signals (the distribution rate and the eight flexibility prices) take the average of the interval `j` steps ahead. The four energy prices are computed cell by cell from `Elec_unit_cost_buy`, with the formula of step 9 and the premium of the lead time `j` of each column. Near the end of the series, the horizon is cut to the last available interval.

**Why.** The market processes of the loop read their prices here (`resolve_marginal_context()` and `settle_market()`), without recomputing averages over `Main_df` at every step.

#### 11. Market commitment matrices

**What it does.** `run_simulation()` calls `prepare_commitments()`, which builds `market_commitments`, a list of twelve tables with the same shape as those of step 10, all at 0:

- energy bought, sold and net on the plan (`Elec_buy_plan_df`, `Elec_sell_plan_df`, `Elec_net_plan_df`);
- the same on the downward flexibility itinerary (`Elec_buy_plan_flex_down_df`, `Elec_sell_plan_flex_down_df`, `Elec_net_plan_flex_down_df`);
- downward flexibility sold and bought back (`Elec_flex_down_sell_plan_df`, `Elec_flex_down_buy_plan_df`);
- upward flexibility sold and bought back (`Elec_flex_up_sell_plan_df`, `Elec_flex_up_buy_plan_df`);
- the committed cost of energy and of flexibility (`Elec_Cost_plan_df`, `Elec_flex_Cost_plan_df`).

**Why.** It is the ledger of the markets. Every time a Scheduling or Piloting market changes the plan of a future interval, the change of energy and its cost are added here by `settle_market()`. Each of the twelve tables gets columns of its own (`data.table::copy()`), because the loop adds to their cells in place (`add_to_table_cells()`, with `set()` of `data.table`): a table has one row per market event of the whole simulation, and copying a column at every addition would cost more the longer the simulation is.

#### 12. Economic analysis accumulators

**What it does.** `run_simulation()` calls `prepare_economic_analysis()`, which builds `economic_analysis`, with three tables and a working index:

- `market`: one row per Scheduling market event and one per Piloting market event, taken from the table of step 7, and one per market slot for Execution. Each event is keyed by the interval its clearing instant falls in, as in step 10. Its accumulator columns start at 0.
- `decision`: one row per Scheduling market event and one per Piloting market event, the same events as `market`. It holds the totals of each decision: the cost of the energy bought, the revenue of the energy sold, the revenue of the flexibility sold, the cost of the flexibility bought back, and the `Reward` the optimizer maximised over its horizon. They start at 0.
- `slot`: one row per market slot of the simulation. Its accumulator columns start at 0.
- `index`: for each slot, its Scheduling, Piloting and Execution rows of `market`. It is used during the loop and dropped at step 14.

The tables get columns of their own (`data.table::copy()`), because the loop adds to their cells in place, as in step 11.

When several markets clear at the same instant, each slot is attributed to one of them only. It goes to the Scheduling market if the slot is inside that market's control horizon, to Execution if it is the slot being delivered, and to the Piloting market otherwise.

**Why.** The matrices of steps 10 and 11 hold values per market event and step ahead, but nothing that adds up to "what this market did in total" or "what happened in this slot in total". The `market` and `slot` tables give that picture, and `decision` keeps what each decision itself did, apart from the rows of `Main_df` it planned. See `99_Readme/Economic_Data_Structures.md`.

## C. Simulation

### 13. Main simulation loop

**The state of the simulation.** `run_simulation()` gathers what the preparation steps produced into one list, the state of the simulation, and calls `simulate()` (`03_Functions/`) with it and with `parameters`. The state holds everything the loop reads, other than the parameters, and everything it updates:

- `Main_df`;
- `assets`, with the table of each asset;
- `full_market_information`, the prices of step 10, which the loop only reads;
- `market_commitments` and `economic_analysis`, the accumulators of steps 11 and 12;
- `paths`, for the C++ modules the workers compile.

`parameters` is only read. `simulate()` takes the elements out of the list once and works on them. The loop is the only writer of the state: the functions it calls return what has to be written, and the loop writes it. Every write into `Main_df` or into the table of an asset goes through `data.table::set()`, which writes into the existing columns, so no table is copied during the loop.

The markets and the execution do not work on the tables themselves. A market takes a piece (`build_market_piece()`, `03_Functions/`): over its rows, the rows of `Main_df` as the table of the system and the rows of the table of each asset, all plain data frames. An asset works on its view (`piece_asset_view()`), which joins the table of the system and the table of the asset with every column once, in the order of `joined_column_order()` (`03_Functions/`), the one `join_asset_tables()` uses, taking each column whole, without copying it, so a write in the view never reaches the piece. A piece can carry the layout of its views (`piece_layout()`, `03_Functions/`): for each asset, which table each column of its view comes from. A view and an absorb use it only if it still describes the tables, and work the positions out again otherwise. The genetic algorithm lays out the piece once, before it evaluates the candidates. It first adds to the table of the system the working columns every evaluation writes (`piece_working_columns()`), so no evaluation adds a column and the layout stays valid in all of them. What the asset changes comes back to its table (`piece_absorb_asset()`), with the net electricity of the system summed again over the assets (`sum_asset_energy()`, once for all the net columns). The valuation of the committed recovery (`committed_recovery_cost()`), the genetic algorithm (`optimize_control_step()`) and the evaluation of a candidate (`evaluate_control()`) work on the piece, and simulate the plan of each asset in its view. The derivation of the itineraries, the hand-over of a tail and the reward work on the piece too: each asset copies its plan in its table, takes the state of a tail on row 1 of its table and is judged in its view, and the phases, the commitments and the reward are written in the table of the system. The window of the system (`system_flex_window()`) and the holding of a window (`system_hold_window()`) work on the piece too: the system writes the phases in its table, each asset drafts, draws or holds in its view, and what it draws comes back into its table with the net electricity summed again. The window builder hands back a new piece and never changes the piece it receives. The execution keeps joining `Main_df` with each asset in turn, with `join_asset_tables()`, which takes each column held by both tables from the table of the asset: the net electricity (with a single asset it is the sum `Main_df` holds) and the inputs, which are equal in both. What a market or an execution step returns is written back by `apply_table_writes()` (`03_Functions/`) into the table that holds each column: the columns of an asset into its table, the others into `Main_df`. When a write changes the net electricity of the building in an itinerary, `apply_table_writes()` writes again, on the same rows, the column of the same name of `Main_df` as the sum over the assets (`sum_asset_energy()`, `03_Functions/`). So the energy of the system is always the sum of the energy of its assets. The commitments of the system are those the market computes over its piece, which with a single asset are those of the building, and they are held in the table of the system of the piece.

**Before the loop.** `simulate()` prepares four things:

- **The tables.** It creates at 0 every column of `parameters$needed_cols` that `Main_df` does not hold yet, and every column of `parameters$asset_cols` of its type that the table of an asset does not hold yet, and turns the numeric columns into `double`. This avoids type errors when a function writes decimal values into a column created as whole numbers. Then it turns `Main_df` and the table of each asset into data.tables.
- **The initial state.** For each asset, it calls the operation `initial_state` of the model of its type, which writes the first row of every context of its table. For a building, `building_initial_state()` writes it from its `model`, in its entry of `parameters$assets`: `Ti` and `Te` from `Ti_0` and `Te_0`, and the heat of the first timestep from `Qh_0` and `Qc_0`.
- **`simulation_control`.** A control object with two sets of indexes: global ones, over the whole `Main_df`, and local ones, over the piece each market works on. It also holds the market columns of the current row, the aim, the settings of the flexibility window and the calculation mode. `market_time`, the full list of market intervals, is built as well; it turns an instant into a column of the matrices of steps 10 and 11. So is `market_index`, the market events of both families and the periods they trade (`market_event_index()`, once per family): the market columns of `Main_df` do not change during the loop, so this list is built once for the whole simulation.
- **The worker cluster**, when `parallel == 1`. `start_worker_cluster()` (`03_Functions/`) creates the worker processes of the genetic algorithm once for the whole simulation. It registers them as the `foreach` backend, sets their random streams (see step 3), exports every function of `sim` to them and compiles the C++ modules of the types of model on each of them. Each worker holds those functions in its own global environment, and its own compiled engine there. With workers, the fitness function of the genetic algorithm is evaluated in them, so `optimize_modes()` gives it the global environment as its own: there each worker finds the functions and the data of the optimization. These are the expensive steps of using workers, and doing them once instead of in every optimization roughly halves the time of a parallel run. Each optimization then only sends the cluster the data of its own market. With `parallel == 0` there is no cluster.

**The loop.** A `for` loop runs once for every row of `Main_df`, in order. At each row:

**0. Market parameters.** It copies the twelve market columns of the row into `simulation_control`.

**1. Scheduling process, when a Scheduling market clears on this row.** The loop calls `run_market_role(prefix = "Sched", ...)` (`03_Functions/`). The function checks `is_market_active()` on `Sched_Market_Name` (true unless the value is empty, `NA` or `"0"`) and, if a market clears, does the following steps. It returns `Main_df`, `assets`, `market_commitments` and `economic_analysis`, which the loop assigns back:

1. **Indexes.** `resolve_market_index()` (`03_Functions/`) finds the rows of the bid time, the start of the period, the end of the optimization horizon and the end of the period. From them it derives the ranges of the period, of the optimization horizon and of the control horizon over `Main_df`. `to_local_indexes()` (`03_Functions/`) then shifts them to the same ranges over the piece cut next. A market controls the time steps of its period, and each row holds the step that ends at it. So the control horizon (`idx_ctrl`) and the optimization horizon (`idx_horizon`) start at the row after the start of the period. The row at the start of the period is the initial condition of the optimization: its step, and its energy, belong to the interval before. A market whose period holds no time step stops the run; step 7 never places one.
2. **Forecast.** `context_forecast_step()` (`03_Functions/`) writes `Text_forec`, `SolarR_forec` and `T_ext_24h_forec` over the period, into `Main_df`; `copy_asset_inputs()` (`03_Functions/`) then writes the same values into the table of each asset whose type declares them as inputs, before the piece is built. With `weather_forecast_type = "inaccurate"`, it calls `imperfect_forecast()` (`03_Functions/`). That function blends the real future value with the average of the same hours over the previous `weather_forecast_n_days_back` days. The weight of that history is `min(1, weather_forecast_weight_history * hours ahead / 24)`, so the forecast gets less reliable the further ahead it looks. `T_ext_24h_forec` is the `T_ext_24h` of the bid time row, that is the mean measured `Text` of the day before the date the market clears, constant over the whole period and the same with both forecast types: the plan never reads the mean temperature of a day that has not ended when the market clears, while the execution keeps the measured `T_ext_24h` of each day.
3. **Piece.** `build_market_piece()` takes the rows of the period from `Main_df`, as the table of the system, and from the table of each asset. It first checks that the `time` of each table is the one of `Main_df`, and that every other column both hold, apart from the net electricity of the system, has the same values on those rows; if not, the run stops.
4. **Market.** Three functions of `03_Functions/` run in turn:
    - `resolve_marginal_context()` fixes, before anything is optimized, the reference against which every candidate is valued. That reference is made of:
        - the energy already committed per market interval (`E_orig_base_by_market`);
        - the flexibility already committed on each leg (`E_orig_expflex_down_by_market`, `E_orig_expflex_up_by_market`);
        - the market prices;
        - the revenue discount factors of each interval.

      With `price_forecast_type = "inaccurate"`, the market does not see the true prices beyond its control horizon: it sees what the markets already know. `price_estimate_sources()` decides, once per market, where the price of each interval beyond the control horizon is read from, by three rules applied in order:
        1. The price of the last earlier market that traded that interval. An earlier market is one that cleared before this one, of either family, Scheduling or Piloting. It traded the interval if the interval falls in its period.
        2. If no earlier market traded it, the price of the same interval one day before: from this market, if its control period holds that interval, or else from the last earlier market that traded it.
        3. If neither rule gives a price, the mean of this market's published prices.

      `market_index`, the list of the market events and their periods that `simulate()` builds once before the loop with `market_event_index()`, is where that search looks. `estimate_price_signal()` then applies the same sources to each of the thirteen price signals. The activation probabilities are not prices, so they keep their values. With `price_forecast_type = "accurate"`, the true prices are used over the whole horizon.
    - `run_market_process(prefix = "Sched", ...)` runs the whole market process:
        - It checks that the index ranges are coherent.
        - It resolves the aim of this market with `map_optimization_aim()`. The aim goes down the call chain with the control metadata (`simulation_control$evaluation$optimization_aim`) and as an argument of `reward_function()`: `parameters` is only read during the simulation.
        - It starts the plan from the executed state, through the operation `plan_start_state` of the model of each asset (`building_plan_start_state()`). `Ti`, `Te`, `Act_heat`, `Act_cool`, `Thermostat_heat`, `Thermostat_cool`, `Q_heat` and `Q_cool` of the plan at the bid time take their `_exec` values: the state the building actually reached there under the real weather, and the heat its systems gave in the step that ends there, which the execution step of the row before has already written. The heat is part of the state because a fraction `inertial_fact` of it reaches the indoor air in the first step of the plan. Earlier markets planned that state with their own forecasts, so starting from the real one keeps their forecast errors from carrying over. From there the plan follows the forecast of this market. The flexibility itineraries are copies of the plan, so they start from the same state.
        - If the control period starts after the bid time, it simulates that gap, for each asset in its view, with the plan it already has, filling missing setpoints with those of the lowest-numbered mode (the operations `default_control` and `execute_step` of the model of the building: `lowest_mode_setpoints()`, and `implement_control_step()`, which calls `period_calculation()`). When a flexibility window whose Commitment Phase starts in the gap runs into the horizon, the gap is extended to the end of its Recovery Phase (`pre_horizon_window_tails()`, which reads the table of the system). `derive_flex_itineraries()` projects both flexibility itineraries over the gap, on the piece of that period, without changing any commitment, and `hand_over_window_tail()` hands the optimization what it needs to continue the tail of each such window. The state the window left and the system that provides it are read, for each asset, from its view, by the operation `tail_state` of its model (`building_tail_state()`), and handed over in lists named by the `asset_id`.
        - It optimizes over the optimization horizon, on a piece that starts at the row of the start of the period, as its initial condition, and runs to the end of the horizon. The genetic algorithm has, for each asset with genes, one gene per market interval of the horizon; the initial row is not one of them. It optimizes according to the aim: `optimize_control_step()` for `energy` and `flexibility`; for `operation`, the operation `simulate_itinerary` of the model (`period_calculation()`) with the setpoints already present (a row of the horizon that no market has planned yet takes the default control of its asset, `lowest_mode_setpoints()` for a building), then `derive_flex_itineraries()` to restate over the recomputed plan the flexibility already committed, buying back the part of the market interval that no longer fits the commitment margin, and `reward_function()` so that the market reports its reward, although it decides nothing with it; `evaluate_control()` alone for `operationflex`. Any other aim stops the run. Before it optimizes, `committed_recovery_cost()` simulates the committed plan and draws over it the flexibility already committed, to value its Recovery Phase; it hands that derivation back with the plan and the control it was drawn with. The `operation` and `operationflex` aims keep the plan they were given, so when the plan they simulate and their control are identical to those, they take that derivation instead of calling `derive_flex_itineraries()` a second time: the result is the same. Whatever the aim, when an asset cannot redraw a commitment of the market interval, because it would raise both thermal systems or because the plan leaves it no room (with both heating and cooling, on an upward window whose system the prudence rule leaves undecided), the assets that redraw it cover what they can with their common fraction, and the assets that refuse it hold what is missing within the limits of their equipment (`system_hold_window()`, through the operations `hold_room` and `window_hold` of each model; for a building `building_hold_room()` and `hold_standing_window()`, whose ceiling is measured at the forecast outdoor temperature `Text_forec`, the one the plan is simulated with): the part that does not fit is bought back, each asset that holds counts, on that leg, as technically infeasible in the reward, and the market reports it with a warning.
        - It writes the resulting `_plan`, `_plan_flex_down` and `_plan_flex_up` columns into the table of each asset of the piece, and the commitments into the table of the system, over the control horizon, whatever the aim. With the `operation` and `operationflex` aims the setpoints are the ones the market was given, and the plan written is that plan simulated with the forecast of the moment, from the executed state: its energy is renominated, and the flexibility restated or sold is measured against the plan that is written. The phase columns `Flex_phase_down_plan` and `Flex_phase_up_plan` are never written: they are the optimizer's own working labels, created in the working tables of the search by `derive_flex_itineraries()`, and `Main_df` does not hold them.
    - The result is then booked in two steps. The asset side writes the itineraries, and the system side settles the market. Neither function writes into a table: each returns its writes (`main_df_writes`), and `run_market_role()` applies them, in order, after each call, with `apply_table_writes()`, which writes each column into the table that holds it. In the steps below, whatever goes into `Main_df` or into the table of the building is returned this way.
    - `write_itineraries()` writes the decision into the itineraries of the assets. It returns the writes of each asset, the `_plan` and `_plan_flex_*` columns, which go into its table, and those of the system, the commitments of the two legs (`Elec_flex_down_plan` and `Elec_flex_up_plan`), which go into `Main_df`, as absolute values on the control rows. `run_market_role()` applies those of each asset, then those of the system. The net electricity of the system in the plan and in the flexibility itineraries is then written into `Main_df` as the sum over the assets. Before applying them, `run_market_role()` keeps a copy of the energy of every row: the net electricity of the system in the plan and in the downward itinerary (named by `system_net_energy_column()`), the flexibility committed on each leg, and the market interval of the row. After applying them, it takes the same columns again. These two tables are all the settlement sees of the building.
    - `settle_market(prefix = "Sched", ...)` settles the decision. It works only with energy per market interval, commitments, prices and amounts, and it reads the net electricity of the system through `system_net_energy()`:
        1. It finds the row of this event in the matrices and the market intervals of the control horizon.
        2. It attributes each of those intervals to a row of `economic_analysis$market`, following the attribution rule of step 12.
        3. It adds up, per interval, the energy before and after this market, for the base energy, the energy with flexibility and the explicit flexibility of each leg. Only two things are committed: the energy of the `_plan` itinerary and the flexibility of the Commitment Phase. The energy of the Recovery Phase depends on the service being called, so it steers the decision but is never settled.
        4. It adds the differences to `market_commitments`. From here on, every interval is valued at once, element by element, and every addition to `market_commitments` and `economic_analysis` is made in place (`add_to_table_cells()`), in the order of the intervals, so the tables are returned without copying their columns.
        5. It values the explicit flexibility traded, both legs (`value_flex_operation()`), at the commitment price of each leg, into `Elec_flex_Cost_plan_df` and `Main_df$Elec_flex_commitment_revenue_h`. The cash flow of an interval is spread over its rows weighted by the commitment of each leg after the decision. The market pays for a commitment whether or not the service is called. The execution price is paid for an activation, so it belongs to the execution phase, which does not simulate flexibility yet. The optimizer still counts the expected execution revenue, the execution price times the activation probability, in its reward. It adds the flexibility sold and bought back of this decision to its row of `economic_analysis$decision`, as `Flex_sell_revenue` and `Flex_purchase_cost`.
        6. It values the change of the base energy commitment (`propagate_differential_cost()` and `calc_differential_cost()`) into `Elec_Cost_plan_df` and `Main_df$Elec_market_net_cost_h`, spread over the rows of each interval weighted by the net electricity of the system in the plan after the decision. It splits the same change into new purchases, buybacks, new sales and resales (`split_market_operation()`), adds them to `economic_analysis` (`accumulate_market_operation()`), and adds their totals to the decision's row of `economic_analysis$decision`, as `Energy_purchase_cost` and `Energy_sell_revenue`.
        7. It books on the decision's row of `economic_analysis$decision` the total reward of the decision over its optimization horizon (`Reward`).
5. **Reset.** `reset_index_list()` (`03_Functions/`) sets every index back to 0.

**2. Piloting process, when a Piloting market clears on this row.** The loop calls the same function, `run_market_role(prefix = "Pilot", ...)`. It does the same steps, with the `Pilot_` columns. Scheduling and Piloting book energy and flexibility in the same way. The only difference is in `economic_analysis`, where `prefix` decides which market a slot is attributed to.

**`model_type_contract()`** (`03_Functions/`) is the contract of a type of model. It dispatches on the type and calls the function that gives the table of operations of that type; for the type `Building` that is `building_model_contract()` (`05_Models/01_Building/03_Functions/`), which binds each operation to the function of the building that carries it out. Every operation is a named function: the operations that are a line are auxiliary functions written in the file of the contract of the type, after it (for example `building_reads_rest_net()` or `battery_can_hold()`), so the table holds the same functions on every call and nothing is created again each time a contract is asked for. A new type of model has a folder in `05_Models/` and one branch in `model_type_contract()`. The market, the genetic algorithm, the reward and the execution never call the model of an asset by its own name: they take the contract of its type, by the `asset_type` of the asset registry, and call the operation they need. Every type supplies the same operations, with the same arguments and results. Each operation receives `asset`, the entry of its asset in `parameters$assets`, which holds the parameters of the asset; the functions of the building it calls receive it too. For the type `Building` the operations are these:

- `load_parameters`: the parameter groups of the asset, read from the files of its configuration folder (`load_building_parameters()`), in step 2.
- `new_table`: the table of the asset on the time grid, in step 2 (`building_new_table()`).
- `prepare_year`: the preparation of the table that needs the whole year, the climate of each day of a building (`prepare_climate()`) and the geometry of the sun of a photovoltaic installation (`photovoltaic_solar_geometry()`), in step 4.
- `prepare_period`: the preparation of the table on the simulated period, the occupancy, the scheduling window and the comfort bands of a building, in step 6 (`building_prepare_period()`).
- `gene_options`: the number of options of each gene of the asset in its block of the chromosome, the number of setpoint modes (`building_gene_options()`).
- `decode_genes`: the setpoints of each market interval from the block of the asset, one mode per interval (`decode_building_genes()`), with the `Deadband` of the building and the setpoints beyond the horizon of the system.
- `default_control`: the setpoints of a row that no market has determined, those of the lowest-numbered mode, with the `Deadband` of the building (`lowest_mode_setpoints()`).
- `plan_start_state`: the start of the plan of the asset from its executed state, on the first row of the chunk (`building_plan_start_state()`).
- `simulate_itinerary`: the simulation of one itinerary over a piece (`period_calculation()`).
- `comfort`: the comfort term of the reward, weighed with the `alpha_comfort` of the asset (`comfort_term()`).
- `window_feasible`: whether the flexibility windows of one leg keep the technical rules of the asset; for a building, that they do not raise both systems over the plan (`flex_window_is_feasible()`).
- `slot_offer`: whether the asset may have something to offer on a new window of one leg starting in a market interval; for a building, that it consumes in the interval (down) or that the prudence rule names a system (up) (`building_slot_offer()`).
- `window_draft`: the draft of the contribution of the asset to one flexibility window of the system, of one leg, over the rows, phases and fractions the system fixed: what it would draw in the Commitment Phase before the commitment margin, and its margin data (`flex_window_draft()`).
- `margin_fit`: the fit of the margin data of the asset alone inside the band of the system, when it is the only asset that contributes to the window (`apply_commitment_margin()`).
- `margin_energy`: the electricity of each row of the margin data of the asset for given quantities, for a building its heating and cooling (`building_margin_energy()`).
- `window_contribution`: the contribution of the asset to the window, with its draft and with what the commitment margin of the set left, with the technical rules of its type (`flex_evaluation()`).
- `restate_systems`: the systems with which the asset may redraw a window already sold when it cannot redraw it as it would sell it: for a building, heating and cooling when the prudence rule leaves an upward window undecided, with the one preferred when both deliver what was sold (`building_restate_systems()`).
- `hold_room`: the most electricity the asset can hold, row by row, of a window already sold that it does not redraw, within the limits of its equipment (`building_hold_room()` for a building, `battery_hold_room()` for a battery).
- `window_hold`: the holding of a commitment already sold on the electricity itinerary of the leg of the asset, within the limits of its equipment. It receives the window held: the phase of each row, the row where the control horizon closes and, for an asset that offers alternatives for the Recovery Phase, the one to draw it with. A building holds the Commitment Phase alone and does not read the window held (`hold_standing_window()`); a battery also carries its leg out until the close of the control horizon (`battery_window_hold()`).
- `continue_window_tail`: the Neutral and Recovery Phases of a window whose Commitment Phase ended before the piece (`continue_standing_tail()`).
- `tail_state`: the state a window left at the start of the horizon and the system that provides it (`building_tail_state()`).
- `execute_step`: the execution of one step with the control already decided (`implement_control_step()`).
- `reads_rest_net`: whether the asset reads the net electricity of the rest of the system. The assets that read it are simulated after those that do not (`asset_simulation_order()`), and their view holds `Elec_rest_<itinerary>`, the sum of the electricity of the assets simulated before them, written by `write_rest_net()`. A building and a photovoltaic installation do not read it, and a battery does.
- `stored_energy_change`: the change of the energy the asset stores on each row of one itinerary, on the side of the system, which the reward values as stored energy. A building and a photovoltaic installation give `NULL`, and a battery gives its change of energy (`battery_stored_energy_change()`).
- `recovery_choices`: the alternatives with which the asset may draw the Recovery Phase of a flexibility window, in the order they are tried. A building and a photovoltaic installation give `NULL`, and a battery gives `minimum` and `plan`. `build_recovery_valuation()` asks it of every asset and gives `NULL` when none offers alternatives; otherwise it gives the alternatives, the assets that choose, the context of the market and the cache of the reward of the plan. `choose_recovery()` takes the pieces drawn with each alternative and keeps the one with the best reward: for each piece it reads the cost of the energy the Recovery Phase moves and the value of the energy the leg leaves stored (`flex_leg_reward_terms()`), and the gain of a piece over the first one is the difference of the first plus the difference of the second, discounted when it is an income. The first piece wins a tie.
- `variable_registry`: the path of the variable registry of the type, which declares the columns of its table (`building_variable_registry()`), read by `load_needed_columns()`.
- `initial_state`: the initial condition of the asset, written into the first row of its table, in step 3 of `simulate()` (`building_initial_state()`).
- `can_hold`: whether the asset can keep its electricity apart from its plan in a flexibility itinerary, a physical capability of its equipment; a building can (`building_can_hold()`) and so can a battery. `derive_flex_itineraries()` names as holders of a window already sold only the assets that can.

**The type `Photovoltaic`.** `model_type_contract()` gives, for the type `Photovoltaic`, the table of `photovoltaic_model_contract()` (`05_Models/02_Photovoltaic/03_Functions/`). A photovoltaic installation has no control, no genes and no comfort, and it cannot move its electricity in time. Its production depends only on the weather. `photovoltaic_generation()`, the operation `simulate_itinerary`, writes on rows 2 to n of the chunk, never on row 1, the production of each step. In the plan and in the two flexibility itineraries it takes the forecast of the weather (`SolarR_forec`, `Text_forec`), and in the execution the measured one (`SolarR`, `Text`). In each step it reads the elevation of the sun and the cosine of the incidence from the table, and `plane_of_array_irradiance()` takes the radiation at 0 if it is negative, splits it into direct and diffuse with `Diffuse_threshold` and `Min_sun_elevation` (the direct normal irradiance is limited to `Solar_constant`), and projects it on the plane of the modules with an isotropic sky and the albedo: that is `G_poa`. It computes the temperature of the cells (`T_cell`) from the outdoor temperature, `G_poa` and the NOCT, the power of the modules from the area, the efficiency, the DC losses and the temperature coefficient, the power of the inverter from its efficiency, limited to its maximum power, and multiplies it by the duration of the step: that is `Elec_PV`, and `Elec_total` is minus `Elec_PV`. The operation `execute_step`, `photovoltaic_execute_step()`, calls it for the rows of the step. `new_table` and `variable_registry` use `Simulation_Variables_Photovoltaic.txt`, and the table of the installation holds `G_poa`, `T_cell`, `Elec_PV` and `Elec_total` of the four contexts, and the three columns of the geometry of the sun. `can_hold` is FALSE, `gene_options` is 0, `default_control` is an empty list, `comfort` is 0 on every row, `window_feasible` is TRUE, `slot_offer` is FALSE, and the operations on a window (`window_draft`, `window_contribution`, `restate_systems`, `hold_room`, `window_hold`, `continue_window_tail`, `tail_state`) return what they receive or an empty answer. `decode_genes`, `margin_fit` and `margin_energy` stop with a message if they are called. These operations are written in the table itself, because each one is a line.

**The type `Battery`.** `model_type_contract()` gives, for the type `Battery`, the table of `battery_model_contract()` (`05_Models/03_Battery/03_Functions/`). A battery charges from the system and discharges into it, and is operated in one of five modes on each market interval (`battery_modes()`): charge from the surplus of the rest of the system, charge, discharge to cover the import of the rest of the system, discharge, and stop. The operations `load_parameters` (`load_battery_parameters()`), `variable_registry` (`battery_variable_registry()`) and `new_table` (`battery_new_table()`) work: the table of a battery holds `Mode`, `Stored_energy`, `Elec_rest`, `Elec_charge`, `Elec_discharge` and `Elec_total` of the four contexts, from `Simulation_Variables_Battery.txt`. `initial_state` (`battery_initial_state()`) writes `SOC_initial * Capacity` as the stored energy of row 1 of the four contexts, and `plan_start_state` (`battery_plan_start_state()`) starts the plan from the stored energy of the execution. `simulate_itinerary` (`battery_simulate_itinerary()`) and `execute_step` (`battery_execute_step()`) compute, for each row, the electricity the battery takes from the system and gives to it, and the energy it stores. The mode of the row (`battery_mode_request()`) turns the net electricity of the rest of the system of the row, `Elec_rest`, into a request of energy, and `battery_trajectory()` clips it with the limits of the battery: the maximum powers, the state of charge between `SOC_min` and `SOC_max`, the efficiencies of charge and discharge, and the self-discharge. The steps of `battery_trajectory()`, the free trajectory of `battery_free_trajectory()` and the two bisections of the windows below (the factor of the battery, `battery_factor_search()`, and the correction of the Recovery Phase, `battery_recovery_correction()`) run in the compiled module of the battery, `battery_trajectory_cpp.cpp`, with the same operations in the same order as R would make them; the R functions check their inputs and call it. The energy stored in a row is exactly the limit when the limit stops the battery. A battery never charges and discharges in the same row. The execution keeps the mode of the plan and works over the real net electricity of the rest of the system. A row with no mode (`NA`) is a row that no market has decided: the battery stops on it, and the mode of the stop is written. A mode 0, like any mode that is not one of the five, is not valid and stops the run. The two flexibility itineraries follow the energy of the plan, from the energy they have stored, clipped by the limits. `prepare_year` and `prepare_period` return the table as it comes, because a battery has nothing to prepare. The operation `gene_options` gives 5, one option per mode, `decode_genes` (`decode_battery_genes()`) turns the genes of the battery, one mode per market interval, into the control table of `period` and `Mode`, and `default_control` gives the stop mode, with which the rows that no market has decided are filled. `comfort` is 0 on every row, because a battery changes no room. `window_feasible` (`battery_window_feasible()`) judges the rows of the Commitment and Recovery Phases of a leg: the electricity of each row within the maximum powers, and the stored energy within `SOC_min` and `SOC_max`. `stored_energy_change` (`battery_stored_energy_change()`) gives, for each row of an itinerary, the energy the battery stores in it on the side of the system, computed from the electricity it takes and gives and from its self-discharge, with a value of 0 in row 1. The windows of a new sale work through five operations. `slot_offer` (`battery_slot_offer()`) says whether the battery has something to give, or to take, on the leg in a market interval: it is not already at the full power of the leg, and it has energy to move or a charge, or a discharge, to stop. `window_draft` (`battery_window_draft()`) drafts the electricity of the Commitment Phase: the leg follows the electricity it had before the window, and the window moves it, row by row, towards the limit of the leg (the discharge power downward, the charge power upward) by a factor that combines the fraction of flexibility of the row and a factor of the battery between 0 and 1. That factor is the largest one with which the leg breaks no limit of the battery until the end of the Neutral Phase (the free trajectory of `battery_free_trajectory()`, which computes the energy with no clipping and marks the steps that break a limit), found by bisection by `battery_factor_search()`. `margin_fit` (`battery_margin_fit()`) and `margin_energy` apply the commitment margin to the electricity, which is linear in the share of the departure that the margin leaves, so the share of each market interval has a closed form. `window_contribution` (`battery_window_contribution()`) draws the leg: the electricity of the draft in the Commitment Phase and the electricity of the leg before the window in the Neutral and Recovery Phases. The leg has to be carried out until the row where the control horizon closes. If the energy it would store breaks a limit of the battery, the Recovery Phase is corrected (`battery_recovery_correction()`): the battery buys energy after a downward window and sells it after an upward one, at one power over the Recovery Phase, or at what a step can still take when its request is already close to the power of the battery, so that a step where the plan is at full power does not stop the correction of the others, and the least power that keeps the leg inside the limits is found by bisection. The correction gives back what the window took, and never more: a step takes no more than the energy that brings the leg back to the energy it had stored before the window, so the correction stops where the leg is back on that energy, and the leg follows it from there. A leg that went past that energy could break, later in the stretch, the limit that the energy of the leg before the window only just keeps. The factor of a window that restates a commitment, and that of a hold, are found with the same correction. When the plan meets both limits of the stored energy within the stretch, the leg that gives back what the window took has to meet it within the tolerance on both: when the power the bisection leaves breaks the other limit, it is interpolated between the last two powers of the bisection to the one that brings the stored energy exactly to the limit, and kept if the leg is then carried out. If the most the battery can do does not keep it, the battery refuses the window with the reason `no_recovery` (`flex_refused()`). When the window carries the alternative `plan` in `recovery`, the correction is the one that returns the stored energy to what the leg had before the window at the end of the Recovery Phase, or the most the battery can do, never less than the least correction. `battery_draw_leg()` writes the leg over the rows of the window and carries the difference of the stored energy to the rows after it, which keep their electricity. A battery can hold energy of a window already sold, and the holding works through two operations. `hold_room` (`battery_hold_room()`) gives, row by row, the most it can hold: the distance between the electricity its leg has on the row and the most it can discharge there (downward) or charge (upward), with its power, its energy limits, its efficiencies and its self-discharge. `window_hold` (`battery_window_hold()`) holds what the system asks of it: the request of the leg moved by that energy is cut by the limits of the battery, and what it moves is the most it can hold. The leg has to be carried out until the close of the control horizon too, so the Recovery Phase of the window held is corrected as in a window it draws, with the least correction or with the return to the energy it had stored before the hold. If the correction does not keep the leg inside the limits, the battery holds a factor of what it can, found by bisection by `battery_factor_search()`, and never refuses: what it does not hold is bought again. If not even holding nothing keeps the leg inside the limits, it holds nothing. `battery_draw_leg()` writes the leg and carries the difference to the rows after it. `restate_systems` gives `NULL`, a battery has no system to choose when it redraws a window already sold. A window that restates a commitment already sold is never refused by the battery for its Recovery Phase: its draft takes the largest factor with which the least correction of the Recovery Phase carries the leg out until the close of the control horizon (`battery_recovery_correction()`, through `battery_factor_search()`), the window is drawn as the plan allows, and what the battery does not reach is bought again. When the battery has nothing to offer on it, its draft or its contribution says that it accepts it with no energy (`accepted`), and the derivation does not ask it to hold what the other assets do not reach. `tail_state` (`battery_tail_state()`) gives the energy the leg of a battery stores at the start of the horizon, and no system. `continue_window_tail` (`battery_continue_window_tail()`) continues the tail of a window whose Commitment Phase ended before the piece: the leg follows the electricity of the plan from the energy the window left, and has to be carried out until the close of the control horizon, so the Recovery Phase of the tail is corrected as in a window the battery draws, with the least correction or with the return to the energy of the plan at the end of the Recovery Phase. A tail cannot be refused: when no correction keeps the leg inside the limits, the battery makes the largest one it can. `battery_draw_leg()` writes the leg over the rows of the tail and carries the difference to the rows after it. The operations of one line are written in the table itself.

The genetic algorithm takes the contract of each asset of the registry, for its block of the chromosome, and so do the reward, the window of the system (`system_flex_window()`), the margin of the set (`system_commitment_margin()`), the restatement of the windows already sold (`derive_flex_itineraries()`) and their holding (`system_hold_window()`), for the comfort, the technical rules, the contribution of each asset, its electricity, the system it redraws a window with and what it holds. Every other caller takes the contract of the single asset it works on. Inside the type, the functions of the building call each other directly: `flex_evaluation()` and `implement_control_step()` call `period_calculation()`, for example. The search filters and the hold of a standing window still read the building directly.

**`optimize_control_step()`** (`03_Functions/`), for the `energy` and `flexibility` aims:

- It works on the piece of the market, and the worker cluster receives that piece. It does not overwrite `Text`, `SolarR` and `T_ext_24h`: in the plan contexts `period_calculation()` reads `Text_forec`, `SolarR_forec` and `T_ext_24h_forec`, so the optimizer never sees the real weather.
- Then it calls `optimize_modes()`, which adds the working columns of the system to the piece (`piece_working_columns()`) and lays it out (`piece_layout()`) before the genetic algorithm, so the worker processes receive it laid out. The genetic algorithm has a chromosome made of blocks, one per asset with genes, one after the other in the order of the asset registry. `chromosome_layout()` lays them out: each block holds one gene per market slot of the horizon, and each gene is a whole number between 1 and the number of options of its asset, which the operation `gene_options` of its model gives (`building_gene_options()`, the number of setpoint modes). An asset whose type has no genes takes no block. When no asset has genes, the chromosome is empty: `optimize_modes()` does not call the genetic algorithm, it returns an empty control list, and `optimize_control_step()` evaluates the plan of every asset as it is. With a registry of one building, the chromosome is its block, one mode per market slot. The operators of the genetic algorithm (`ga_population_int()`, `ga_crossover_int()`, `ga_mutation_int()`) keep each gene a whole number within its own bounds. Each candidate goes through `fitness_funct_optimize_mode()`, then `decode_chromosome()`, which hands each block to the operation `decode_genes` of the model of its asset and gives the control of each asset, by its `asset_id` (for the building, `decode_building_genes()`, which calls `maxmode()` and then `convert_modes_to_setpoints()`, which reads the heating and cooling setpoints of each mode from the `setpoint_modes` of the building and adds the ±`Deadband/2` band), then `evaluate_control()`, which simulates the building with its control.
    - With `parallel == 1`, it runs on the worker cluster that `simulate()` created before the loop (see step 13). It only sends it the data the optimization needs, and it does not stop it. With `parallel == 0`, it runs the same evaluation loop in the main process.
- With the best controls found, it calls `evaluate_control()` once more to get the final piece.

**`evaluate_control()`** (`03_Functions/`), the evaluation used both by the genetic algorithm and by the final step above:

1. The operation `simulate_itinerary` of the model (`period_calculation()`) simulates each asset, in its view, under the forecast with the control of the candidate for that asset, into the `_plan` columns. The assets are simulated in the order of `asset_simulation_order()`: first those that do not read the net electricity of the rest of the system, in the order of the registry, then those that do (the operation `reads_rest_net` of their model). Before it simulates one of the latter, `write_rest_net()` writes in its view `Elec_rest_plan`, the sum of the `Elec_total_plan` of the assets simulated before. The same order and the same column are used wherever the plan of the assets is simulated: the gap before the optimization, the aim `operation` of a market, and the value of the committed recovery (`committed_recovery_cost()`). The plan of each asset goes back into its table, and the net electricity of the system is summed again.
2. `derive_flex_itineraries()`, on the piece, with the state of a tail on row 1 of the table of each asset, builds the `_plan_flex_down` and `_plan_flex_up` itineraries from `_plan` and from the flexibility already committed by earlier markets, so that a new market starts from what is already sold. No window label is stored, so `reconstruct_flex_phases()` reads the windows of each leg from its committed energy (`Elec_flex_down_plan`, `Elec_flex_up_plan`). A market interval with committed energy on any of its rows is in a Commitment Phase, and consecutive such intervals form one window, cut if it is longer than `commitment_phase_length_max`. A gap of intervals with no committed energy between two committed stretches stays inside one window when it is shorter than the Neutral and Recovery Phases together and the two stretches with the gap still fit within `commitment_phase_length_max`: two windows that one market sees are always further apart than that, because a new window is never opened over the phases of another one. Intervals with no committed energy at the edges of a window are not part of it. The Neutral and Recovery Phases follow the last committed interval of each window. The rows of the market interval are restated inside the commitment margin (guard zone) and the others are projected without it. The minimum flexibility does not apply to a restatement: an interval of the guard zone that the new plan can only hold below the minimum keeps what it holds, and only the shortfall is bought back. A window never includes row 1 of the piece, its initial condition: a window that started before the piece is rebuilt from row 2, with the state handed over on row 1 as its initial condition. The system of a standing upward window is not stored, so each building finds it again (the operation `restate_systems` of the model, `building_restate_systems()`): the one `resolve_flex_up_hvac()` names, or, when that prudence rule is undecided, the one of heating and cooling with which the building contributes and the window reaches what was sold (the one that uses more electricity in the plan over `flex_up_horizon_long` when both do). When neither reaches it, the one with which the building contributes and the window commits more of what was sold is kept, and the window is restated with it as with a system the rule names: at the most it allows, with the shortfall of the guard zone bought back and no penalty. The building refuses the window only when it is refused with both systems. With several undecided buildings, their systems are chosen one building at a time, in the order of the asset registry. The rule only decides whether a new upward window is sold. Only the assets that can hold electricity apart from their plan (the operation `can_hold` of their model) hold a standing window or count in its penalty, in the order of the registry. All the assets redraw a standing window with one fraction for the set. An asset that has nothing to offer on it may accept it with no energy instead of refusing it (a battery always does, through the field `accepted` of its draft or contribution, and `system_flex_window()` then returns it in `empty_contributors`): it holds nothing, and what the others do not reach is bought back. When some assets refuse it, the others cover what they can, the assets that refuse it hold what is still missing, part by part (guard zone and projection), sharing it in proportion to what each can hold (`system_hold_window()`, which also marks the rows held as Commitment Phase in the table of the system, and, when a battery holds energy there, the Neutral and Recovery Phases of the window, so that the cost of the energy the battery buys or sells in its Recovery Phase is valued), and the rest is bought back; each holder receives the window held, with the phase of each of its rows and the row where the control horizon closes; when no asset redraws it, every asset holds it. It returns, in `held`, each asset and leg that holds energy (more than `flex_energy_tol`) of a window with rows in the guard zone, with at least one asset per leg (the first holder in the order of the registry when none keeps energy there), and the caller writes how many they are in `Standing_commitment_held_legs_plan`. When an asset offers alternatives for the Recovery Phase (a battery), the derivation receives the valuation of `build_recovery_valuation()`: a window it restates is found with the fractions that reproduce what was sold, without the valuation, because the commitment does not depend on the Recovery Phase, and it is then built once more with the fractions kept and the valuation, so that the battery draws the Recovery Phase with the alternative that has the best reward; the commitment is the same, and the derivation stops if it is not. A window that is held is chosen in `system_hold_window()` in the same way: each alternative holds the same share again and `choose_recovery()` keeps the piece with the best reward. The tail of a window handed over from the initialization period is continued over the candidate's plan, by each asset with its own state and system (the operation `continue_window_tail` of its model: `continue_standing_tail()` for a building, `battery_continue_window_tail()` for a battery), with the row where the control horizon closes and the halvings and the tolerance of a bisection, which a battery uses to correct the Recovery Phase of the tail. With the valuation, each asset that offers alternatives for the Recovery Phase and has a state in the tail continues it again with each of the other alternatives, from the view it had before, on a copy of the piece; an alternative that draws the same electricity is not valued, and `choose_recovery()` keeps the piece with the best reward on the leg. Each window is drawn as a window of the system (`system_flex_window()`), to which the building contributes (`flex_evaluation()`), and what it commits is read on the net electricity of the system (`system_flex_commitment()`). The rows and phases of a standing window, the piece with its phases and the view of each asset do not depend on the fraction, so they are prepared once per window, at its first build (`system_flex_frame()`), and handed to every build of the bisection. It also writes the commitment the itineraries carry, the commitment of the net, so that a market that places no new window keeps the one it restated.
3. `reward_function()` computes the reward of that plan.
4. With the `flexibility` or `operationflex` aims, it searches for flexibility, in two phases that run the same algorithm on one leg each. Every candidate window is built on the piece by the window of the system, which hands back a new piece with the window and leaves the piece it receives as it was; the candidate is valued on that new piece with `reward_function()`, and the best window is kept; the views are laid out once before the search (`piece_layout()`):
    - **Phase A, downward.** For each market slot of the horizon, skipping those where no asset consumes (operation `slot_offer`) or where downward flexibility is worth nothing, it tries a flexibility event that grows slot by slot (the window of the system, `system_flex_window()`, on the downward leg, then `reward_function()`), and keeps the one with the best reward. It stops growing when the reward stops improving or at a slot where the flexibility is worth nothing. What a slot is worth is the effective sell price of the leg: the commitment price plus the execution price times the activation probability, read from the marginal context `resolve_marginal_context()` built for the market, so published inside the control horizon and estimated beyond it, the same prices the reward uses. A slot with only an execution price is searched. A window starts at the instant its first slot starts: its Commitment Phase begins on the first row of the slot, and the row before, the last row of the previous slot, is the initial condition of the window. The first row of the piece is its initial condition, so it is in no slot of the search.
    - **Phase B, upward.** The same, on the piece phase A leaves, with `system_flex_window()` on the upward leg. It reads the effective sell price of the upward leg. A slot is skipped when no asset can raise its electricity from it: for a building, when `resolve_flex_up_hvac()` finds no system (operation `slot_offer`).
    - After a window is accepted, the search resumes past its whole window: the Commitment Phase and the Neutral and Recovery Phases that follow it. When nothing is accepted from a slot, it moves on to the next slot, so every start slot is tested.
    - Windows never overlap within a phase, but a phase B window may overlap a phase A window: each leg has its own columns, and the interval then carries a commitment on each.
    - The valuation is built before the derivation, on the plan of the candidate (`evaluate_control()`, `committed_recovery_cost()` and the operation aim of `run_market_process()` build it), so that the windows already sold are drawn with the same choice as a new one. `build_recovery_valuation()` asks every asset of the registry, through the operation `recovery_choices`, how it may draw the Recovery Phase of a window. With a building and a photovoltaic installation it gives `NULL` and nothing changes. With a battery it keeps the alternatives, the cache of the reward of the plan and the context of the market, and `system_flex_window()` receives them with every candidate: after building the window with the first alternative, it draws the contribution of the battery again with each of the others, with the same draft and margin, and `choose_recovery()` keeps the window with the best reward (see `recovery_choices` in the contract).
    - The candidates of a phase change only the itinerary of their own leg. So, before each phase, `build_reward_cache()` resolves once what they all share: the discount factors, the market interval of each row, the energy and distribution cost of the plan, and the terms of the other leg, with its feasibility. Each candidate is then valued with `reward_function()` on that cache, and only the terms of the leg being searched are computed again. The reward is the same as without the cache.

**`system_flex_window()`** (`03_Functions/`) builds one flexibility window of the system, of one leg, downward or upward. The window is of the set of assets: the system fixes its phases, the commitment margin is one, of the set, each asset draws its contribution, and the commitment is that of the net. Both legs go through the same steps, so that their results can be compared:

Steps 1 to 3 and the view of each asset are the frame of the window (`system_flex_frame()`): they do not depend on the fraction of flexibility, so a caller that builds the same window with several fractions, as the restatement does, prepares them once and hands them over. The fraction of each row is set at every call.

1. A new window must fit inside the control horizon, or it is refused. Its last time step may end on the last row of the control horizon. A window that restates a commitment already sold is drawn wherever it falls.
2. It takes the rows of the window: the row before its first row, as its initial condition, and then the time steps of its three phases. Each phase holds the rows whose instant is from its start to just before its end, so the phases are whole time steps and match those `reconstruct_flex_phases()` reads back. The lengths of the phases are of the system, the same for every asset. For each row of the Commitment Phase it fixes the time step, whether the row is in the guard zone, and its fraction of flexibility, the same for every asset. An upward window with no row in its Commitment Phase has nothing to offer.
3. It marks the three phases of the window in `Flex_phase_down_plan` or `Flex_phase_up_plan` of the table of the system (1 Commitment, 2 Neutral, 3 Recovery).
4. Each asset of the registry drafts its contribution, in its view of the piece, which carries the phases, through the operation `window_draft` of its model (`flex_window_draft()` for a building): what it would draw in the Commitment Phase before the commitment margin, and its margin data. An asset that has nothing to offer is left out; on a window that restates a commitment, an asset that accepts it with no energy (`accepted`) is kept apart, and returned in `empty_contributors`.
5. On the rows of the guard zone, `system_commitment_margin()` applies the commitment margin to the set of assets that remain. The margin is one, of the set. Each asset gives the electricity it draws on each row at the limit of the leg, at the ceiling of the window upward and at its floor downward (nothing, for a building, with both systems off). `commitment_margin_bound()` turns the sum of those limits, the market interval of each row and `flexibility_commitment_margin` into the band of each market interval, from energy alone: the net electricity may reach at most the limit of the set less the margin upward, and at least the limit of the set plus the margin downward. With a single asset, the asset fits its itinerary inside that band through the operation `margin_fit` of its model: for a building, `apply_commitment_margin()` finds for each market interval, by bisection in compiled code (`apply_commitment_margin_cpp()`), the deepest scaling of its itinerary whose electricity stays inside the band. With several assets, the departure of every asset from its plan is scaled by one same factor in each market interval, found by bisection on the net electricity, which the operation `margin_energy` of each model gives. Either way the number of halvings is `flexibility_commitment_bisection_steps`, and an interval whose plan is already outside the band keeps the plan. The electricity is computed at the forecast outdoor temperature, the one the window is simulated with. On a new window, it then measures the net electricity each interval sells and brings back to the plan, in every asset, an interval that sells something but less than `minimum_flexibility` times the length of the interval, the minimum `commitment_margin_bound()` gives.
6. Each asset draws its contribution through the operation `window_contribution` of its model (`flex_evaluation()` for a building), with what the margin left, in its view; what it draws comes back into its table, and the net electricity of the system is summed again. An asset that has nothing to offer, or whose contribution breaks the technical rules of its type, contributes nothing, and the others contribute what they can. When an asset contributes nothing, it leaves the set and the margin is applied again to the assets that remain, so that the net of the assets that finally contribute keeps it. When no asset contributes, the window is not built.
7. On the upward leg, it declines the window, reading the net electricity in the table of the system, when it does not rise during the Commitment Phase.
8. On a new window, it checks the electricity each market interval sells, on the net of the table of the system (`system_flex_commitment()`): it refuses the window when an interval sells something but less than its minimum, or when its first or last interval sells nothing. An interval inside the window that sells nothing is a gap of the window.
9. With a valuation of the Recovery Phase, the assets that contribute and offer alternatives (the operation `recovery_choices`) draw their contribution again with each alternative but the first, from their own view and with their draft and the margin of the last round, and their tables replace those of the window built. An alternative whose electricity is the one of the first is dropped. `choose_recovery()` values the window built and the others, and the one with the best reward is kept. The alternatives differ only in the Recovery Phase, so the commitment is the same, and the function stops if it is not.

**`flex_window_draft()`** (`05_Models/01_Building/03_Functions/`) drafts the contribution of a building to a window of the system, over the rows, phases and fractions the system fixed:

1. On the upward leg only, it first asks `resolve_flex_up_hvac()` which system, heating or cooling, may be committed. The building has nothing to offer when the answer is `"none"`. A window that restates a commitment already sold may come with the system of the building, chosen by `derive_flex_itineraries()`, and then the rule is not asked.
2. `flex_commitment_profile()` draws the heating and cooling of the Commitment Phase, before the commitment margin. The downward leg reduces both systems towards zero. The upward leg raises the selected system towards its maximum power and switches the other one off, the mirror of the downward reduction. This profile is the physical side of the window. On the rows of the guard zone, `building_margin_data()` gives the margin data of the building: the heat of the plan and of the itinerary, and the electricity of each row at the limit of the leg (the maximum power of the selected system upward, no heat downward), at the forecast outdoor temperature.

**`flex_evaluation()`** (`05_Models/01_Building/03_Functions/`) draws the contribution of a building to a window of the system, with its draft and with what the commitment margin of the set left. Both legs go through the same steps:

1. `flex_margined_profile()` puts together the heating and cooling of the Commitment Phase: the rows of the guard zone take the heat the margin left, both systems downward, the selected system upward, the other one staying off. The building contributes nothing to a new upward window that raises nothing, because the plan was already at maximum power or the margin left no room.
2. It writes the phases of the system in the rows of the window. On the downward leg, `resolve_flex_down_hvac()` then reads which system ran most during the Commitment Phase: that is the system that provides the contribution.
3. It simulates the window with `period_calculation()`, from its initial condition: with the heat input fixed during the Commitment and Neutral Phases, and with setpoints and a per-step power cap during the Recovery Phase. On the steps whose heat is imposed, `Act_heat` and `Act_cool` are 2 when the imposed heat or cold is above 0, and 0 otherwise; the thermostats keep running their hysteresis in `Thermostat_heat` and `Thermostat_cool`, so the Recovery Phase starts from the state of the thermostat, not from the imposition. The caps come from `build_hvac_lock_caps()`: the system that did not provide the service may keep or reduce its planned power during the Recovery Phase, never increase it.
4. It writes its itinerary of the leg back, without the initial condition, and keeps the contribution only if `check_recovery_convergence()` finds the flexibility itinerary of the building back on its plan by the end of the control horizon, for a new window, and if `flex_window_is_feasible()` finds that the windows of the leg do not raise both systems of the building over the plan. Otherwise the building refuses the window and contributes nothing.

**`period_calculation()`** (`05_Models/01_Building/03_Functions/`) calls no other R function except `period_simulation_cpp()`. It checks the context and the setpoints and picks the columns of the context: `_exec`, `_plan`, `_plan_flex_down` or `_plan_flex_up`. It applies the setpoints of `set_point_df`, one per market interval, when they are given, and leaves the whole physical calculation to the C++ engine. That engine runs the two-capacity thermal model with hysteresis, the heat pump curves, the choice of ventilation and the electricity and comfort results. The COP and the electricity of each step come from `heat_pump_cop_cpp()` and `heat_pump_electricity_step()`, the same compiled electrical model that the R functions call. The results are written back into the columns of the context. The engine computes no cost: costs are always resolved afterwards in R, by `reward_function()` when planning and by `settle_execution()` when executing.

**`reward_function()`** (`03_Functions/`) needs `marginal_context` and stops without it. It brings together the two sides of the reward, the assets and the system:

- **The asset side.** For each asset of the registry, the operation `comfort` of its model (`comfort_term()` for a building) reads the comfort flags of the three itineraries and gives the comfort term of each row, weighed with the `alpha_comfort` of the asset; the comfort term of the reward is the sum over the assets. The technical feasibility penalty is also resolved here, asset by asset and leg by leg, with the operation `window_feasible` of each model (`flex_window_is_feasible()` for a building), because it depends on the flexibility windows of each asset. The rules are checked within each asset: two buildings may raise one system each. `build_reward_cache()` keeps the answer of each asset for the leg that a search holds fixed.
- **The system side.** `system_energy_rows()` takes from the piece only what the system knows of each row: its market interval, the net electricity of the system in each of the three itineraries (read with `system_net_energy()`), the phase of each flexibility leg, the prices and the activation probabilities. When an asset stores energy (a battery), it also holds the change of the energy the assets store on each row of the three itineraries, which `system_stored_energy()` adds up from the operation `stored_energy_change` of each model. `economic_terms()` computes every economic term from those rows, with the commitments and prices of `marginal_context`. It never sees a temperature, a mode or a setpoint.

`economic_terms()` values each candidate against the reference fixed by `resolve_marginal_context()`. Every economic term is differential: it values only the change against what earlier markets already committed, so an itinerary identical to the committed one is valued 0, whatever the aim. The terms are these:

- **Energy.** `compute_marginal_energy_cost()` adds up the candidate energy (`Elec_total_plan`) per market interval, and `calc_differential_cost()` values the change against `E_orig_base_by_market` at the four energy prices.
- **Distribution.** The distribution cost is settled on the net energy of each time step: a step pays the rate on the energy it exchanges, in either direction. `compute_marginal_distribution_cost()` values the plan the same way. The gross volume of an interval is the sum of the absolute energy of its time steps, and the change of that volume against the committed one is valued at the distribution rate, `-distribution_rate * (gross_new - gross_orig)`. Buying or selling more always adds cost, and buying or selling less always saves it; steps of one interval that import and export do not offset each other. It applies to the base energy only, never to flexibility.
- **Flexibility**, whatever the aim. With the `energy` and `operation` aims no new window is placed, so these terms value the flexibility that earlier markets sold and that the itineraries restate: a plan that can no longer hold it pays for buying part of it back. Inside the control horizon that change is the one the market settles. After the close of the control horizon no market may change the commitment yet, so a candidate is valued there at most at the commitment that stands (`beyond_control_by_market`): holding it is worth nothing, falling short costs the re-purchase a later market will have to make, and drawing more sells nothing. Where nothing is committed, they are 0. It computes the committed volume of each leg over its own Commitment Phase, from the net electricity of the system in each itinerary: `Elec_flex_down_plan = Elec_total_plan - Elec_total_plan_flex_down` and `Elec_flex_up_plan = Elec_total_plan_flex_up - Elec_total_plan`. `flex_leg_reward_terms()` computes the terms of each leg, and `compute_marginal_flex_revenue()` values its committed volume. The revenue is split in two:
    - `Elec_flex_com_revenue_plan`, the certain payment for the commitment, at the commitment prices;
    - `Elec_flex_exec_revenue_plan`, the payment for the execution, at the execution prices weighted by the activation probability of each leg. It also carries `compute_recovery_energy_cost()`, the energy the building would move during the Recovery Phase if the service were called, valued as the change against the cost of the itineraries already committed. `committed_recovery_cost()` resolves that cost once per market, before the optimization: it simulates the committed plan of each asset, in its view, with the forecast of the market, draws over it the flexibility already sold with `derive_flex_itineraries()`, and values its Recovery Phase with the same prices.
- **Stored energy**, only when an asset stores energy (a battery). The energy left stored at the end of the horizon is worth what it saves to buy later, so it is valued at the mean price at which the market buys energy over its horizon (`stored_energy_price`, resolved by `resolve_marginal_context()`), and, when the change is an income, discounted with the factor of the last interval of the horizon (`stored_energy_discount`). `system_stored_energy()` adds up, from the operation `stored_energy_change` of each model, the change of the energy the assets store on each row of the three itineraries, and `compute_stored_energy_value()` values it. When `reward_function()` builds the cache of the reward itself, on the piece it values, it resolves that change once and hands it to `build_reward_cache()`, and so does `committed_recovery_cost()`. Two terms result, each one as the change against the committed itineraries, as every other term:
    - the energy the plan leaves stored (`build_reward_cache()`), which `economic_terms()` adds to `Elec_Cost_plan`;
    - the energy each leg leaves stored against the plan, weighted by the activation probability of the leg (`flex_leg_reward_terms()`), which `economic_terms()` adds to `Elec_flex_exec_revenue_plan`, since it is part of the same conditional scenario as the Recovery Phase: if the service were called and the Recovery Phase did not bring the energy back, the leg would leave it stored or spent.
    `committed_recovery_cost()` resolves the committed values together with the cost of the Recovery Phase. With no battery in the registry none of this exists, and the terms are the ones above.
- **Discount.** Each economic term is resolved interval by interval. Where an interval's cash flow is an income, it is multiplied by `(1 - Revenue_discount_per_hour/100)^n`, with `n` the hours from the decision to that interval (`apply_revenue_discount()` and `revenue_discount_factor()`). Expenses and comfort are never discounted. The discount only steers the decision: `settle_market()` settles the chosen candidate at the market's own prices.

The reward is the sum over the buildings of `alpha_comfort * Performance`, each with the `alpha_comfort` of its building, plus `alpha_cost * (the economic terms) + Technical_feasibility_penalty`: `comfort_term()` gives the first part, `economic_terms()` the second, and `reward_function()` adds the three. The last term is −1e9 for each asset and flexibility leg whose windows are technically infeasible (the operation `window_feasible`), −1e9 more for each asset and leg that holds a window already sold that it could not draw over the plan (`Standing_commitment_held_legs_plan`), and 0 otherwise. `Performance` counts, as a negative number of hours, the time steps, occupied or not, where any of the three itineraries is outside its own comfort band. It has no unit: `alpha_comfort` is in 1/h, one per building, from `18_Comfort_parameters.csv` of its folder, and `alpha_cost` in 1/EUR, one for the system. Every economic term already carries its sign, income positive and expense negative, so they are simply added.

**`calc_differential_cost()`** (`03_Functions/`) values a change of a net commitment, from `E_orig` to `E_new`, at four prices: `P_import_buy`, `P_import_sell`, `P_export_buy` and `P_export_sell`. Within each regime, "buy" is a new commitment and "sell" undoes an earlier one. Within the same sign, the part that grows is valued at the price of a new commitment and the part that shrinks at the price of undoing one. When the commitment crosses zero, the old commitment is undone in full and the new one is valued in full. `split_market_operation()` resolves the same cases into four operations: new purchase, buyback, new sale and resale.

**3. Execution process, always.** This runs at every row, whether or not a market clears. It takes only the current row and the next one:

For each asset of the registry, in turn, in the order of `asset_simulation_order()` (the assets that read the net electricity of the rest of the system, such as a battery, execute after the others):

1. It joins `Main_df` and the table of that asset over those two rows into `period_chunk` (`join_asset_tables()`).
2. If the asset reads the net electricity of the rest of the system, `write_rest_net()` first writes in `period_chunk` its `Elec_rest_exec`: the electricity that the assets executed before it have had in the step. The operation `execute_step` of the model of the asset, `implement_control_step(..., calculation_context = "execution")` (`05_Models/01_Building/03_Functions/`) for a building, calls `period_calculation()` with the real weather and the setpoints already decided, copied from the plan, and advances the real state (`Ti_exec`, `Te_exec`, and the rest) by one step. It is the asset side of the execution: it works with the physics of the asset, and writes no money and no column of the system.
3. It writes back only the execution columns that the table of the asset holds, not its inputs (`apply_table_writes()`), and the executed net electricity of the system into `Main_df` as the sum over the assets. The plan columns were already written by the market integration.

Then, once per row, with every asset executed:

4. The loop fixes `Elec_total_no_flex`, the net electricity of the system the row would have used without an executed flexibility event: until flexibility execution is simulated, the executed net electricity that `Main_df` holds (`system_net_energy()`).
5. `settle_execution()` (`03_Functions/`) is the system side of the execution. It receives only the net electricity of the system in the plan and in the executed itinerary of the new row (read from `Main_df` with `system_net_energy()`), the prices of the row and the cash flow its markets already accumulated. It knows nothing of temperatures, modes or setpoints. It is settled once per row, never per asset. It returns the costs of the new row, which the loop writes into `Main_df` (`apply_table_writes()` with no asset, together with `Elec_total_no_flex`):
    - `Elec_deviations_net_cost_h`: `calc_differential_cost()` from the plan energy, the last plan in force, to the executed energy. It values the deviation from the plan, not the whole energy.
    - `Elec_cost_distr_h`: `-Elec_unit_cost_distribution * |executed energy|`, always an expense: the net energy the time step exchanges with the grid, which is what the distribution cost is settled on.
    - `Elec_net_cost_h = Elec_market_net_cost_h + Elec_deviations_net_cost_h`.

**4. Progress.** It computes the elapsed and the remaining time and, if `verbose`, writes the line of the step with `console_message()`: the label `TRANSFER`, the instant where the energy transfer of the step ends, the step number and the two times as `h:mm:ss`. It is one line per step, whatever the number and the type of the assets. The lines of the run share three columns, a label, an instant and a text (`console_message()`). A market writes its own `MARKET` line when it ends, at its bid time. `imperfect_forecast()` writes nothing: the first market whose forecast has instants with no history writes a `WARNING` line, and `simulate()` reports the totals when the run ends.

**After the loop** `simulate()` stops the worker cluster, if there is one, and stores the total duration in `execution_time$t_process`. It returns the final state: the same elements, with `Main_df`, `assets`, `market_commitments` and `economic_analysis` updated, plus `execution_time`. `run_simulation()` takes each element back from it, and steps 14 and 15 read them.

**Why.** This is the core of the MPC. At every timestep it decides whether to plan (Scheduling and Piloting, under forecast, with the reward optimized by the genetic algorithm), and it always executes one real physical step with the real weather and the setpoints already decided. Keeping the execution columns apart from the plan columns is what allows comparing, in the same table of the building, what was planned with what really happened.

## D. Post-process and export

### 14. Complete the economic analysis

**What it does.** `run_simulation()` calls `finalize()`, which completes `economic_analysis` once the loop is over. The Scheduling and Piloting flows were already added during the loop; this step adds the execution phase and the reported fractions. When `verbose` is TRUE, it writes one `RUN` line with `console_message()`, with the size of the completed tables.

1. It finds the market slot of every row.
2. It values the execution phase per market slot: the move from the last committed plan (`Elec_total_plan`) to what was delivered (`Elec_total_exec`), netted over the slot and valued at its own prices, split with `split_market_operation()` into new purchases, buybacks, new sales and resales. Netting per slot matters: energy is traded per slot, and a deviation that only moves energy between two timesteps of the same slot is not a purchase plus a sale.
3. It fills the Execution rows of `economic_analysis$market`.
4. It fills the remaining columns of `economic_analysis$slot`.
5. It derives the reported fractions, whose denominators are only known once every market has traded. A fraction whose denominator is 0 is `NA`. `Frac_rebuy_resale_value` is also `NA` when its denominator, the net money of the slot, is within `flex_energy_tol` of 0, and in a slot whose traded energy and committed flexibility add up to less than `flex_energy_tol`: its denominator is then only the money left by positions bought and sold back, close to 0, and the fraction would take extreme values.
6. It drops the working columns and the index.

A resale undoes an earlier purchase, so it reduces `Cost_energy_bought`; a buyback undoes an earlier sale, so it reduces `Revenue_energy_sold`. See `99_Readme/Economic_Data_Structures.md`.

### 15. Export results

**What it does.** `run_simulation()` calls `write_outputs()`, which creates `paths$output_path` if it does not exist and writes the output tables, each as `.csv` and `.rds`:

- `Main_df_computed`: the columns of `Main_df`, common and system, in the order of `02_Needed_cols.csv`.
- `<asset_id>_df_computed`, one table per asset: `time` first, then the columns of its type of model, one row per row of `Main_df`. Those columns include its inputs, copies of the columns of `Main_df` with the same name (`Text`, `SolarR`, `T_ext_24h`, `Text_forec`, `SolarR_forec` and `T_ext_24h_forec` for a building; no `T_ext_24h` nor `T_ext_24h_forec` for a photovoltaic installation). `Elec_total_<itinerary>` there is the net electricity of the asset, and `Main_df_computed` holds the sum.
- `Sinthetized_df_computed`: one summary row. It holds the settings of `parameters$optimization` and the totals of the run: comfort (the comfort of every building added up), energy in and out, flexibility committed and executed on each leg, energy cost and revenue, flexibility revenue, distribution cost, reward and `execution_time$t_process`. The money columns follow the sign convention, income positive and expense negative.
- `Economic_analysis_market_computed`, `Economic_analysis_decision_computed` and `Economic_analysis_slot_computed`: the three tables of `economic_analysis`. The reward of `Sinthetized_df_computed` is the sum of the `Reward` of the decisions.

After the export, `run_simulation()` returns `Main_df`, `assets`, `market_commitments`, `economic_analysis` and `execution_time`, and `Main.R` keeps them in `results`.

**Why.** It is the single output point of the simulation; every later analysis starts from these files. See `99_Readme/Input_Output_Files.md` for their columns.

## Scope notes

- This document follows the normal path of `run_simulation()` with the shipped configuration: `Complex_Market_Config = "yes"`, `Price_emulation = 1` and `parallel = 1`. The other branches (the basic market mode, the accurate forecasts, `parallel = 0`) are described in each step, marked as such.
- Flexibility execution is not simulated. The columns reserved for it (`Elec_flex_execution_revenue_h`, `Elec_flex_deviations_net_cost_h`) stay at 0, and `Elec_total_no_flex` equals `Elec_total_exec`. The execution price of flexibility is therefore never paid: the markets settle the commitment price only.
- `economic_analysis$decision$Reward` holds, on the row of each market decision, the total reward of that decision over its optimization horizon. It is not a reward of the executed trajectory.
